# Known limitations

[中文](limitations.md) | [Back to README](../README.en.md)

This page lists only the **current** boundaries and unverified areas; implemented behavior lives in the [Usage guide](usage.en.md) and [Architecture and behavior](architecture.en.md).

## Runtime and compatibility

- The DSH plugin API targets **0.2.2**; the validated build is **0.2.2-rc.1** (current latest), and later DSH versions are untested.
- Build, test and release workflows use **Node.js 24**; the repository pins neither `engines` nor `.nvmrc`.
- Validated platforms are macOS (Web + DSH Desktop) and Windows (DSH Desktop); Linux is not verified.
- The browser half requires `@deepseek-ai/dsh-client-locale` in the deployment (DSH Web 0.2.2 includes it); a minimal profile without it cannot mount the switch or cards.
- The plugin settings page needs `dsh-settings` / `dsh-client-ui-settings`; interactive-page export needs the `webServer` service. Missing services hide the corresponding UI.
- After a client-bundle change, **restart `dsh-web`**; a page refresh is not enough.

## Answers and rendering

- A card appears at the **end of its turn**; during generation the process row only shows "Interactive answer".
- The model can produce invalid OpenUI Lang; the Host returns precise validation errors and the model usually repairs within the same turn (1–2 attempts observed), but success is not guaranteed.
- The generation prompt is about 10K tokens and is sent only when the switch hits the session; off means no prompt and no tool schema. Article pages take longer to generate and render.
- Maps use OpenFreeMap tiles, routes use the OSRM demo, and searched photos use Wikipedia/Wikimedia; offline maps fall back to a place list and searched photos to placeholders.
- An explicit `Image` source never searches for a substitute: a missing file, a file above 10 MiB, a type outside PNG/JPEG/WebP/GIF (including SVG), or a failed http(s) load shows an error placeholder. Inline `data:image/…;base64` is capped at 512 KiB decoded; the 40 MP pixel cap is pre-read from PNG/JPEG/GIF/WebP headers for both local files and inline data URIs (unknown headers are checked after load, so an extreme decompression bomb can still allocate decode memory before rejection; remote images keep the browser's behavior); absolute paths are read by the Host process through workspace-files, which is not limited to the workspace and can read files outside it, so another Host/device may point at a different file; an image is a render-time snapshot that needs a re-render after the file changes; wrap a Markdown image destination containing spaces or parentheses in `<>`. Local files need the workspace-files service from DSH 0.2.2; an older Host shows the 'This Host cannot read local images' placeholder, and a service that appears after the card already rendered the error placeholder requires a re-render to retry (the resolver identity is stable), an `http(s)` SVG URL still renders through the browser's `<img>` behavior (no scripts) while only path/data SVG is rejected, and local images inside a sandboxed `HtmlView` are not supported.
- KaTeX relies on the DSH shell's global styles; removing them degrades `Math` to plain text.
- `/iui` Host replies, command-palette descriptions and README screenshots stay English; only browser UI copy follows the DSH language.

- **Experimental document answer:** it only simulates message-body presentation — the page still lives in a turn-tail `render_ui` result rather than in the message; copying, search and transcript Markdown export omit its body; the document page has no card editing entry or revision history; only the Web renderer (Web/Desktop) shows it, and clients that do not render plugin cards (TUI/headless) show nothing; results replay from what was recorded, so the switch only affects new answers. The switch will be removed once DSH supports in-message UI natively.
## Export

- Image export does not include sandboxed iframe content (`HtmlView` mini-games); maps rely on the WebGL buffer and fall back to the map's own degraded view when WebGL is unavailable.
- All cards in one turn are combined into one image, and export captures the **current interactive state** (checks, filters), not the initial state. Export waits for images/search for up to ~12.5 seconds and otherwise captures placeholders.
- Interactive-page export inlines the renderer, theme and all cards into one HTML (roughly 3.4–4.9 MB); maps, searched photos and remote image URLs still need the network, while workspace images are read back and inlined as data URLs (32 MiB base64 total) so they render offline. `@ToAssistant` uses the clipboard; when unavailable it shows the message for manual copying. HTML export only inlines local images that are inside the card container and resolved successfully; Popover content (open or closed) is portaled outside it, and inactive branches plus failed/oversized/SVG local images are not collected, so the exported page shows a placeholder. The export waits only for local source resolution (short bound), not for image searches or remote loads.
- Temporary style, templates and on-demand state do not travel with the exported HTML for cross-device editing; the export is the rendered result.

## Templates and styles

- Portable template exchange is v1 and at most **32 KiB (UTF-8)**; only the exchange envelope is accepted, not raw template exports or library backups. Limits are 40 global and 20 session templates.
- Import creates global templates only; session-scope import is not open yet. There are no share codes, live links, batch backups or batch imports.
- External template names and directives enter the prompt as untrusted text; preview and explicit acknowledgement reduce but do not remove prompt-injection risk. Origin/CSRF and tool-permission auditing are still recommended for real deployments.
- Custom light/dark themes apply to the renderer host only; portaled Popovers and sandboxed iframes keep the default theme. Interactive-page export freezes the exported scheme.
- Whether an answer uses a page is a model judgment, not a deterministic rule: the same question may render a page once and answer in Markdown another time; a session style (built-in Auto/Card/Article or a saved template) only decides the layout when a page is rendered and cannot force every answer to render. Auto may choose a free layout directly (no Card/Article shell, recorded by the Host as built-in); a free-layout result has no theme snapshot, so it cannot be saved as a template, and the editor's built-in style-switch targets remain Card/Article. An explicit render request (`/intelligent-ui`, an explicit page/dashboard ask), on-demand generation and artifact edit requests still require a page.

## On-demand, drafts and tabs

- On-demand operations are memory-only: armed state expires after 10 minutes and is lost on restart; completed results survive. One active operation per session; a bound running/clarifying operation refuses re-arm and allows at most two clarification rounds.
- The on-demand hint appears only in the initiating tab, but the Host binds the session's next human message without checking the sending tab; send from the initiating tab.
- Unsent edit drafts are stored per tab in `sessionStorage`: refresh restores them, but **tabs do not share them**; `branch`, `latestRevision`, `submitFailed` and undo records are not persisted, and oversized programs are not stored.
- Cross-tab edit leases use BroadcastChannel and only warn; they do not merge edits or block editing. Without the channel there is no warning, and the Host revision check remains authoritative.

## Block editing and structural operations

- Editable blocks are every direct child of the root `Col` and of the seven allowlisted containers; `@Each`, opaque expressions, shared named expressions, page chrome and pages over the depth/node budget are not editable. The CST node budget is **200**, so very long article pages can be rejected; the structure Apply preview distinguishes `depth`/`nestedTarget` (nesting) from `nodeLimit` (node budget) instead of reporting a node-budget page as too deep.
- Top-level order must contain exactly the base revision's top-level blocks (at most 100); the Host merges the model's edited fragments and leaves unselected blocks byte-identical.
- One request carries at most 12 content edits; instructions are at most 2,000 characters and the global note 4,000. A request with no actual change is rejected.
- Strict protection only detects **identified unselected top-level blocks**; changes inside a selected root block's subtree are not detected.
- A natural-language style adjustment turns a saved/built-in-style page into a result-owned (temporary-style) revision: without a model-provided theme it inherits the session theme rather than the original template theme (template-theme continuity is a follow-up); history shows the source as "block edit" plus the temporary-style badge; old Hosts or non-editable cards do not offer the in-editor style section and keep the footer Adjust style fallback (a missing base registration does not hide the section; sending/applying then reports the error); redirected read-only fallback cards offer neither Save nor Adjust. Each temporary-style revision adds one result-registry snapshot (existing LRU cap).
- Deterministic style switching (zero model) changes style identity, shell and theme only: template directives do not reflow existing content (that needs a model render); Article targets need a page with usable contents and sections, otherwise the client disables them and the Host rejects them (`article_unavailable`); saved templates are live references — changing a theme affects older switch revisions that reference it, and deleting it falls back to the built-in theme; a branch switch uses the explicit branch and never branches automatically; the result is a local revision card that does not enter the assistant message, transcript replay, image/HTML export or other devices; H4 is fixed — after a switch, render_ui order-only/global-only edits use the artifact's recorded style and are no longer rejected by the session style (content edits through edit_ui_blocks are unaffected); sessionStyleScope is only template visibility scope, not an authorization boundary; Save-as-template applies only to theme-bearing temporary style results; it creates a new template without overwriting built-in/existing templates, built-in/saved-template/plain results show no Save entry, there is no update-original or copy-saved-template action, and saving creates no revision.
- Structural operations support duplicate, delete, same-parent/cross-container move and one addition per container; nested-to-root moves, batch undo/GC, and helper cleanup are not supported. Cross-container moves append to the target. Off-screen Carousel anchors may need draw-time clipping (not implemented).
- Structural operations first enter this round's pending queue instead of applying immediately: **Apply** opens the total preview and, once confirmed, the Host records one structural revision atomically. A pure-structure Apply closes the draft only after that revision is recorded; a mixed Apply (model requests, global note or ordering) rebases the draft onto the new revision and auto-sends the remaining request, keeping the chip for a manual send when the composer still holds user prose. Queueing, cancelling a batch edit and removing a chip never lose queued operations or saved block requests. There is still no dedicated "structure changed, saved draft stale" confirmation UI: references that cannot be remapped block Apply as a total-preview conflict instead of being silently dropped.
- Legacy pages need no manual migration: the first time you open editing, revision history or restore, the client registers the currently rendered content as the Host's authoritative base (write-once, never overwritten), after which structure operations, history and restore work. Remaining limits: with an old Host (no registration route) mixed with a new client, registration is unavailable and the affected operations fall back to instruction editing or a re-render; legacy cards never touched by an authoritative operation stay unregistered (no background migration); an LRU-evicted non-current revision program cannot be reconstructed client-side; a registered initial revision shows the registration time in history. The authoritative registry holds at most 200 programs / 50MB.
- Local structure/property revision cards live in browser `localStorage`, render only in the triggering Turn, are not assistant messages, do not participate in image/interactive-page export and are lost across devices.
- Revision-history deletion is a real, **irreversible** Host delete: the initial render cannot be deleted; a revision still referenced as another revision's `baseRevisionId` is refused (`409 revision_referenced`) until the newer revision is deleted. Before deleting a revision a card renders, the client fetches the newest older revision whose program is still retained and which is not owned by a client-local card; when none exists, the rendered revision offers no delete. After the delete, cards still showing that revision roll back to the fallback (keeping their position and callId) and become read-only; the stage selects the rollback target named by the confirmation, stays read-only while it displays that target, and selecting another revision restores editing; **if that fallback target is deleted later, the client resolves the fallback chain to a revision that still exists (depth/cycle bound 20)**. A revision that any card's unsent draft is editing cannot be deleted (that would unmount the canvas and strand the chip on a removed base), and a revision still used as a newer revision's base hides its delete with an explanation (the Host returns a `referenced` field), and a revision that a card's fallback still targets hides Delete when no older fallback exists (so a fallback chain cannot land on a deleted record). A redirected card is read-only, and result-bound actions (Save/Adjust) are hidden on it because the initial row's style is borrowed and has no matching result snapshot. **Without an available fallback, deleting from another card still succeeds and any card still rendering it may stay stale**. The fallback is stored per session in browser `localStorage` within a size budget (the oldest entries are evicted past 20 entries or the character budget, after which a reload may render the deleted revision again), so clearing storage or switching devices loses the rollback; there is no `storage` listener, so a delete in another tab is not reflected immediately, and drafts live in per-tab sessionStorage, so the deletion lock only covers drafts visible in the current tab; rolling back to the initial revision borrows the earliest record's style and may keep the deleted revision's temporaryStyle. A deleted base makes still-referencing drafts fail at send as stale, while the structure route returns `base_missing` and the restore route returns `source_missing`; the `struct_` idempotency ledger entry for the same `operationId` is not removed.
- Edits for multiple artifacts are independent with no cross-artifact transaction: one failure does not roll back other successful revisions. After a Turn, drafts are reconciled by requestId; unfinished drafts return as "not completed, draft kept" for re-attaching and are never auto-retried. Host pending still has a 15-minute TTL; Turn ownership uses a send-time window heuristic, and extreme clock/latency cases are unverified.
- The real-model "partial success" path has not been validated in the real GUI; single-card, two-card, nested-edit and structural-operation success paths have.

## Runtime state and accessibility

- Runtime snapshots are memory-only and lost on refresh; caps are 24 artifacts, 5 revisions per artifact and 64KiB per snapshot. First renders do not inherit history; only a revision with `baseRevisionId` inherits from its base. Third-party internals and edit-canvas interactions are not preserved.
- The edit canvas supports screen readers and keyboard-only use, but has not had a real screen-reader/axe audit. The live region is a single polite slot, so rapid reorders merge announcements; pointer drag announces only on drop.
- Input-orbit forced-colors/touch behavior is validated through Chromium CDP emulation only; real Windows High Contrast, iPad/Safari and dark-theme contrast are unmeasured.
- Visual baselines are manual (5 PNGs) with no automated pixel diff; layout was checked at 390×844, 900×1000 and desktop widths, not across more devices/browsers.
- The update notice asks the npm registry for `latest` from the Host (six-hour success cache, five-minute failure cache, five-second timeout); when an update exists it also reads that tag's `release-notes/<version>.md` highlights from `raw.githubusercontent.com`. If either network is unreachable the notice degrades (no points, or no card at all). DSH 0.2.2-rc.1 has no sidebar slot between New Session and the panel list, so the card mounts into the sidebar DOM (`src/client/sidebar-update.ts`); a changed sidebar shape hides it instead of breaking layout, and DSH upgrades must be watched. The card never covers Plugins / Automation tasks, hides in the collapsed rail, and the "View details" label only opens a highlights popover, clicking the rest of the card opens the plugin detail page, and nothing updates automatically. Release points must be written in `release-notes/<version>.md` and pass the `check:release-notes` gate; a missing file blocks the publish workflow, but the card only shows the Highlights section, not every change.
- `npm run check` does not include the Chrome browser suites; CI (`ci.yml`) runs the local gate on PRs and main (CHANGELOG/PRODUCT/docs-only diffs run just the docs checks; the packed README pair takes the full gate), adds the browser suites on main for code changes, and releases run from a tag-triggered GitHub Actions workflow. `check:release` is not in CI yet (its Linux runner behaviour is unverified) and remains a local pre-release gate. `tsc` does not check `src/client` because DSH platform types are runtime-provided.
