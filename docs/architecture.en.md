## Architecture

With the switch off there is no trace of this tool on the model side; only after it is turned on does the model see the tool, a system prompt section and an on-demand skill. All UI rendering and interaction happen in the browser; the program itself enters the session log as a tool argument and is replayed with history.

## Switch and answer style

![The composer UI control: the three-way switch and Display style below an inset divider](../assets/intelligent-ui-toggle.png)

- **Global defaults:** the Plugin detail page provides **Enable in all sessions**, the global Auto / Card / Article or saved-template style, the **Free-form layout** switch, the experimental **Answer as a document** switch, and the **Export** defaults (image background color, 1x/2x, and whether images/pages remove the `@ToAssistant` follow-up control and its form fields — a Card with prose keeps its prose, only a pure follow-up block disappears whole; on by default). New sessions inherit these values. The page groups them into **Availability**, **Answer style**, **My styles**, **Composition**, **Experimental** and **Export**.
- **Session overrides:** the composer UI control changes only the current session. `/iui on|off|inherit` sets the enable override; `/iui style auto|card|article|inherit|<cs_id>` sets the style override. A session override wins over the global value; `inherit` follows it.
- **Answer styles:** a session style is a layout preference for when a page is rendered, not a requirement to render — the model first decides whether the answer needs a page (structure, visuals, interaction or computation) or reads better as Markdown. `Card` is the compact interactive card; `Article` is a reading layout inside the `render_ui` card (`Toc` + collapsible `Section`s + long Markdown prose); `Auto` lets the model choose Card, Article or a free layout (no Card/Article shell, optional `Toc`/`Section`). A Section body is its own nested flow using the group rhythm; the page-level flow relies on margins only, without an extra flex gap, so section boundaries do not double their blank space.
- **Experimental document mode:** the Plugin detail page's **Experimental → Answer as a document (experimental)** writes the volatile Host setting `documentMode`. When on, an ordinary answer (not an on-demand result, Artifact edit or saved template) uses the document contract: the whole answer lives in one program, `style: "free"`, no Markdown reply; the Host enforces that layout, ignores the session template, and records `document: true` plus `styleSource: "builtin"` in the success value and `presentationMeta`. The client renders such a result as a chrome-less `section.dsh-iui-document`. It creates no Artifact lineage and has no editing entry or revision history; on-demand results (`temporaryStyle`), selected templates and edit requests keep their cards. Results replay from what was recorded, so the switch only affects new answers. Removal path: once DSH supports in-message UI natively, delete the setting field, the document prompt prefix/note, the Host `documentRender` branch and the client `DocumentCard`; recorded results fall back to the card shell.
- **State:** the global enable/style/free-composition/document-mode values live in the Host settings document; session enable, off and style overrides are written atomically to `<DSH_HOME>/dsh-intelligent-ui.json` (`sessions`, `offSessions`, `styles`). Legacy `{ "global": true, "sessions": [...] }` files are still read as migration values.
- The session command log folds into the `intelligent-ui` projection, which carries the current enable/style view, pending state and live `onDemand` (stateVersion 6); the composer control only mirrors the projection, and the Host owns every state decision. The control broadcasts its optimistic view to other tabs over BroadcastChannel; the projection wins once it arrives. The scope menu and the export menu share the same `MenuItem`/`MenuDivider` rows (content-based width with a 208px minimum, one vertical rhythm, consistent selected/hover/disabled states); the scope menu and the style panel both right-align with the chip and keep a 12px gap above the trigger; both use an opaque layer-2 raised surface while inner cards/rows retain the module surface so the layers stay distinct in light and dark mode. The Display style row is always visible, disabled while off, with an inset hairline above it; the style panel is a second level, and its back button returns to the scope menu instead of dismissing every popup. A scope switch only sends the enable command and **never auto-opens** the panel; the panel has exactly two explicit entries — the Display style row, and clicking the already-active scope entry when it resolves to enabled (an off scope, or follow-global while the global switch is off, just closes the menu).
- The switch requires a deployment that composes both `sessionProjections` and `commands` (DSH Web has both by default). If either service is missing, the session controls cannot be displayed or persisted, and the extension falls back to **always on**.

## Custom styles and on-demand operations

### Result style contract

`StyleSnapshot` in `src/shared/style-templates.ts` is schemaVersion 1 (StyleSnapshotV1): `baseLayout: card|article|free`, `directives`, optional `theme`, and optional `suggestedName`. Omitting the theme is the normal case: the result inherits the session theme (the selected template, otherwise the built-in theme). A complete theme is only needed when the page carries its own palette, and only a passed theme is contrast-checked (3:1, 4.5:1 recommended). A result without an explicit theme cannot become a style template because there is no palette to copy. `render_ui` requires `program` and `style`, with optional `title` and mutually exclusive `styleId` or `temporaryStyle`. The temporary snapshot's `baseLayout` must equal `style`; only a current tool call observed and authorized by the Host may use it. New on-demand generation uses `style: "free"` and `temporaryStyle.baseLayout: "free"`; the program determines the layout without Card compactness or an Article reading wrapper. Toc/Section are optional for free results; parser, anchor, theme and authorization checks remain. Legacy card/article snapshots keep their shell and Article checks. Built-in session styles remain Auto/Card/Article; an ordinary Auto render may also use `style: "free"` directly (no `styleId`/`temporaryStyle`, recorded as builtin and replayed as the built-in free layout), while a forced Card/Article session still rejects free. Saved templates use `baseLayout: RenderLayout` (card/article/free). A selected free template uses `style: "free"` and its exact `styleId`, without `temporaryStyle`; the Host retains template ID and layout consistency checks. During on-demand operations the prompt omits session-shell guidance: follow the user’s layout request and ask a focused question if materially unclear, with no silent default. Success includes `statements`, `style`, `styleSource: builtin|template|temporary`, and optional `styleId`/`document`/`warnings`; an ordinary render also records `style`/`styleSource` (and `document: true` in document mode) in `presentationMeta` so a settled free-layout or document result replays, while the snapshot lives in tool arguments rather than a duplicate success field.

The Host enforces layout by operation kind: `generate` requires both `style` and `temporaryStyle.baseLayout` to be `free`; `adjust` requires both to match the snapshot `baseLayout` stored under `parentResultId` (free stays free, legacy card/article keeps its layout). A missing parent snapshot, including eviction by the latest-200 limit, rejects adjustment with an error asking the user to cancel and start a new on-demand generation; model arguments and conversation content cannot establish the parent layout. Rejection neither records a result nor completes the operation; historical tool arguments still replay.

Precedence is authorized temporary style for this call → session override → global default → Auto. A session style only decides the layout when a page is rendered; the model decides whether to render at all (except an explicit render request, `/intelligent-ui`, on-demand generation and artifact edit requests). Temporary styles never write session/global settings. An ordinary call under a selected custom template must pass its exact `styleId` and base layout. Missing templates/catalog fall back to the default client theme; a theme-less temporary snapshot also inherits the selected template or built-in theme instead of staying catalog-independent.

### Operation and session events

`host/on-demand.ts` keeps one Operation per session: Host-generated `operationId`, session/optional client identity, the first human message's `triggerMessageId`, generate/adjust kind, optional `parentResultId`, clarification rounds, result IDs and timestamps. `/iui on-demand [off|<client-instance-token> [adjust <resultId>]]` arms or cancels; the session must be enabled first. While armed, re-arming replaces the active operation without changing the selected style; once a human message has bound the operation (running/clarifying), re-arming is rejected and the caller must cancel explicitly, so a second click cannot revoke an authorization the model is about to use.

States are `armed → running ↔ clarifying → completed`, with `failed`, `cancelled` and `interrupted` exits. Armed intent has a 10-minute TTL checked on access. The controller retains at most 256 sessions without silently evicting active work. Operations are in memory; restart clears their views (without reconstructing interrupted records) and requires re-arming.

A prepended `session/event` listener updates state before projection publication, deduplicates monotonic seq values and constrains tool events by turn. The first human `user/message` binds the operation; injected skill/file context is ignored. DSH appends a step's `system/message` before its first `user/message`, so the ON-DEMAND note must be injected while the operation is **armed** and kept after binding; otherwise the first turn's model never sees the on-demand contract. During a bound on-demand turn, a plain `render_ui` without `temporaryStyle` is rejected so the model must use a temporary snapshot or ask first. `tool/call render_ui` registers its callId (up to 8 attempts); temporary authorization requires the bound message, active state and current callId. After validation and the durable result write, the Host synchronously completes the operation. Late calls lose authorization after completion/cancellation. A completed turn that rendered nothing returns to armed/resume; only error/abort moves the operation to failed/cancelled/interrupted.

`ask_user_question` enters clarifying and blocks temporary render until answered. A matching structured tool result (`answers` array) or callId-tagged `user-question-reply` resumes running; a timeout is not an answer, a question error fails, and at most two rounds are allowed. The prompt requests 1–3 questions per round, with options/free input/skipping when DSH supports them; the extension does not replace the built-in question UI. If the tool is unavailable, text questions degrade the flow; a completed turn without a render enters resume, so the next message continues without an immediate re-arm (except after expiry, restart or failure).

Projection v6 adds nullable `onDemand` (operationId, status, kind, parentResultId, clientInstanceId, resultIds) alongside enable/style/pending. Replaying history does not authorize operations. `OnDemandHint` appears only for armed intent and matching client identity; examples fill without sending and preserve drafts. The Host still binds the next human message in the session without checking its sending tab; this conservative convergence is not message-metadata isolation.

### Saving and template management

`result-store.ts` atomically persists the latest 200 immutable temporary snapshots in `<DSH_HOME>/dsh-intelligent-ui-results.json`: `resultId = tool callId`, sessionId, snapshot, optional parentResultId and createdAt. Each adjustment gets a new callId; there is no separate revisionId in this implementation. Saving uses the clicked result ID. Recorded arguments can still replay after registry eviction, but saving then returns `result_missing`.

`style-store.ts` persists templates in `<DSH_HOME>/dsh-intelligent-ui-styles.json` (still `version: 1`; free is an additive layout value requiring no migration), limited to 40 global and 20 per session. `GET /api/intelligent-ui/styles?sessionId=…` returns global and that session's templates; POST on the same route supports `save`, `saveFromResult`, `update`, `delete`. Routes register only with `webServer` and `connection.requestRejection`, authenticate first, accept JSON up to 64 KiB/15 seconds and return no-store responses.

`saveFromResult` accepts resultId, name, description, scope and optional sessionId; it rejects `baseLayout` (including legacy client shell choices) and browser-provided directives/theme. The Host copies baseLayout/directives/theme exactly from the registered snapshot; a theme-less snapshot answers 400 `no_theme`, and the client hides Save as template because a template needs its own palette. Session scope must match the owning session. Saving neither selects the template nor changes the global default. Duplicate names fail; the server has no separate idempotency key. `update` allows only name/description/directives; `delete` removes a template. The composer manages visible templates; settings manages global templates and file export/import. Deleting the current choice attempts an Auto fallback; other sessions handle stale references as missing templates.

### Portable template exchange v1

The pure shared `src/shared/style-template-exchange.ts` has no React, DOM or DSH dependency and provides `toPortableStyle`, `createStyleExport`, `encodeStyleExport` and `parseStyleExport`. Envelope keys are exactly `kind: "dsh-intelligent-ui/style-template"`, `schemaVersion: 1`, and `template`. Portable fields are constructed in order: `name`, `description`, `baseLayout: card|article|free`, `directives`, `theme`. Missing description becomes `''`; other fields are required. Every level rejects unknown keys, including `__proto__`, `constructor` and `prototype`. Themes reuse `isStyleTheme` hex/enum validation; labels/preferences retain existing bounds and character rules. Names/descriptions also strip Unicode `Cf` and trim; empty or reserved names reject. Themes and palettes are explicitly rebuilt in fixed order, with `JSON.stringify(value, null, 2)` producing identical bytes for the same configuration. Local IDs, scope, sessions, timestamps, package versions, export dates, authors, signatures and checksums are excluded.

Input is checked with `TextEncoder` before parsing, limited to 32 KiB of UTF-8 bytes. File selection checks `File.size` before reading, regardless of filename/MIME. One whole-input Markdown fence with `json` or no language is tolerated; JSON is not searched for in arbitrary prose. External names/descriptions/directives strip `Cf`, `Default_Ignorable_Code_Point` and U+2800; labels also normalize U+2028/U+2029 to spaces. Raw legacy template exports are not supported: raw template objects, store documents such as `{version:1, templates:[…]}` and other non-envelope shapes reject as `invalid_structure` without fuzzy detection. Typed `StyleExchangeError` codes are `empty_input`, `too_large`, `invalid_json`, `invalid_structure`, `unsupported_version` and `invalid_template`; the UI localizes them without exposing raw exceptions.

My styles in Plugin settings and the composer's Display style panel share the export menu (session-scoped templates export from the composer too): both confirm the name/description/full preferences/theme disclosure before exporting `<template-name>.iui-style.json` (application/json), using `fileStem`, an attached noopener anchor, removal and deferred URL revocation. Both import entries (My styles and the composer panel) mount `TemplateImport` and send file/paste input through the same codec, creating global templates only. Preview supports editing name (30), description (100) and preferences (2000), or clearing preferences, while showing layout, light/dark canvas/ink/accent swatches and full preference text. All external content (name, description and preferences) requires explicit acknowledgement, reset when the name or preferences change. External content uses React text nodes/form fields without HTML or Markdown execution. Case-insensitive global name collisions suggest a truncated `(Imported)` name; remaining collisions block confirmation. A full 40-template global catalog disables import, while Host duplicate_name/limit_reached errors remain authoritative. Errors retain input. Busy state plus a synchronous flight guard prevents double submission; the Popover supports Escape, focus return and keyboard cycling.

Confirmation calls `StyleActions.createTemplate` on the existing authenticated `POST /api/intelligent-ui/styles`, with exactly `{op:'save', template:{name,description,baseLayout,directives,theme}, scope:'global'}` and no sessionId. The response must pass `isStyleTemplate`. The Host retains its five-field whitelist, theme/label/preference checks, cross-scope duplicate names, quotas and atomic writes, generating fresh identity/timestamps. Success refreshes the catalog, closes the dialog and announces status, without settings writes or automatic application. Imported templates use the ordinary use/rename/edit/delete/re-export paths. There are no new Host endpoints, store formats or model calls; the composer reuses the same export/import components (export covers session templates, import still writes global templates only) and session-scope import remains deferred. Codes/links/gallery/batch imports are unavailable.

**Compatibility promise**: exchange format v1 contains only portable style configuration and all three current layouts, excluding local identity/session metadata. Plugin versions supporting v1 can import it; unknown versions reject explicitly without downgrade guessing. Raw template exports are out of compatibility scope. Exchange versions are independent of npm versions. Future v2 implementations should retain the v1 parser; adding layouts or removing baseLayout requires explicit format evolution, never silently accepting unknown layouts in v1.

**Trust boundary and plan deviation**: following owner approval (2026-10-24), the current implementation replaces the plan’s mandatory appearance-only import before audit with a disclaimer plus acknowledgement of all external content (name, description and preferences). The plan/reviews are retained. External names and directives enter the prompt while the description is stored/exported only and never enters it; all external content is treated as untrusted text. Preview, edit/clear, acknowledgement and no automatic application mitigate risk without eliminating prompt injection. DISPLAY PREFERENCES/JSON encoding does not isolate execution. DSH’s tool/permission execution layer remains authoritative; execution-layer and real-deployment Origin/CSRF audits are recommended pre-release hardening. This validation checks existing requestRejection delegation and route denial, not real-deployment Origin/CSRF policy or prevention of tool privilege escalation.

### Card themes, actions and security boundaries

`programs.ts` defensively extracts temporary snapshots from recorded arguments, rejects mixed sources/layout mismatch, and skips failed calls or arguments outside the loaded history window. `IntelligentUICards` resolves the temporary snapshot's theme first, then a saved template by `styleId`; a theme-less temporary snapshot inherits the session's selected template theme (the live card and the HTML export share this resolution) and finally falls back to the built-in theme. `resolveStyleThemeVars` maps only whitelisted fields into renderer-host CSS variables. Scheme follows the DSH body marker (system preference outside DSH). Portaled popovers and sandboxed iframes keep the default theme; semantic status colors remain CSS-owned.

Temporary results show a **Temporary style** badge and **Save as template**; on a new Host with an editable card, style adjustment lives in the edit canvas **Style → Change style** section (old Hosts or non-editable cards keep the footer **Adjust style** fallback; redirected read-only fallback cards keep neither), not a separate extension action. The save popover asks only for name/description/availability. The Host copies the original layout and validated theme/directives exactly, leaving the result unchanged and making no model call. Legacy snapshots retain their layout and original save flow. Free templates have a local composition preview and **Free layout** hint, with use/rename/edit preferences/delete actions. Template results retain the DSH card header without the temporary badge or adjust/save actions; free adds no Article wrapper or Toc/Section requirement and uses the template’s light/dark theme. Settings owns global defaults, saved-template management, composition and exports; generation happens in the composer.

Themes accept only light/dark six-digit hex palettes and font/radius/density/shadow enums, rejecting unknown fields, arbitrary CSS/scripts/URLs. Temporary ink/canvas and accent/canvas must reach 3:1 in each scheme, with a warning below 4.5:1. Directives are limited to 2,000 characters. Saved-template directives enter the prompt as a JSON string inside DISPLAY PREFERENCES delimiters, explicitly subordinate to system/tool/safety rules. Temporary directives remain result data, never promoted to system instructions. Models cannot self-arm, save templates or change defaults; the existing `HtmlView` sandbox boundary remains.

Replay accepts free template calls with a valid styleId; free without a source, invalid snapshots and styleId/temporaryStyle mixes still render nothing. Replay and `programsToExportCards` preserve free layout for temporary results and templates; PNG captures the live composition. Standalone HTML uses available page width for free results and retains the 760px measure plus the live 12px card gap for Card/Article results, including mixed exports. Resolved per-result themes and schemes remain frozen in HTML exports.

UI state structure: an in-flight write or command must not be expressed as visual `disabled`. The settings page has no render-visible pending state; saves set `aria-busy` imperatively through `sectionRef`. The composer panel is a separate `StylePanel` that receives only availability (`disabled`) and callbacks, so the parent's `busy`/`pending` is outside its scope; On-demand arming lives inside `StylePicker`. Controls added inside these boundaries therefore cannot receive transient command state and turn a save/style switch into block-wide `disabled`/opacity flashes. Only the control that owns the async operation may disable itself briefly (the On-demand entry, an import submit button). The `:disabled { opacity }` CSS remains, so a new boundary that reintroduces transient `disabled` can still flash; express unavailability through `locked`/`panelDisabled` instead.

## Artifact block editing and arrangement

A rendered page can be revised in place inside its card: an **Edit** entry in the card header turns the body into a read-only canvas plus the **Artifact editor** on the right. The editor keeps content changes and arrangement separate: the user writes change requests per block (a request exists only after saving) and reorders all top-level blocks by dragging or with the keyboard in **Block arrangement**. Both are just parts of one structured request on send; the model calls the tool that matches the request — `edit_ui_blocks` returns only the selected blocks' fragments for content edits, while order-only/global-only requests use `render_ui` once with the complete program — the Host merges and records the result as a new revision of the same artifact, and the card history icon carries the revision number. Content edits, an order-only request (`edits` empty) and a combined request are all valid; the global instruction is optional. One chat can keep several card edit drafts in parallel — one active canvas, one composer chip and one stable `requestId` per draft; one send merges up to 3 artifacts' requests into one user message (multiple V1 envelopes), and the Host applies each request and records its own revision.

### Block recognition and stable references

- The edit entry appears only on editable cards: the program parses, its root is a `Col`, at least one top-level block is recognizable and the call has finished; temporary-style results are editable too (content edits and natural-language style edits inside the editor — see M3-4 and B1). `extractArtifactBlocks` in `src/shared/artifact-blocks.ts` parses programs against the same `vendor/spec.json` used by the Host.
- Editable blocks are **every direct element child of the root `Col`** (and the direct children of the seven nested containers, M4-6); `Caption`, `Divider`, `Spacer`, `Toc` and a root `Title` are ordinary editable blocks now instead of page chrome. The only safety exclusions left are `@Each` templates, opaque expressions, shared named expressions, depth/node limits, and duplicating subtrees that contain `Section`/`Toc` anchors. `ArtifactBlock` carries `blockId` (`b<originalIndex>`), `nodePath` (`root[rootIndex]`), `originalIndex` (1-based position among the base revision's editable blocks), `rootIndex` (0-based position among all root children), `componentType`, `kind` (section/card/table/chart/interactive/drawing/media/container/divider/spacer/toc/heading/caption/content) and optional `statementId`/`title`. Titles come from the block's `Title`/`Caption`, `Section.title`, `Toc.items`, `Table.columns` or first text, never from screen coordinates.
- Identity is stable within the base revision: arrangement only changes `targetOrder` and never rewrites `blockId`/`originalIndex`/`nodePath`; the request also carries the `selectionOrder` assigned when a request is saved. Reordering therefore keeps block references and the numbering of saved requests unchanged.
- `wrapProgramForBlockEditing` rewrites only the root statement: it wraps each editable child in the internal `BlockSlot("bN", N, [...])` component and keeps the other children and the root tail verbatim, so the edit view renders the wrapped program through the normal renderer and the outlines, numbering and popovers attach to real DOM nodes. `BlockSlot` is registered only in `library.ts`'s `blockEditLibrary` (enabled by the `blockSlots` switch in `render.tsx`) and never enters the model-facing catalog (57 components unchanged).
- When the program shape is unsupported it returns a reason (unparsed / no_root / incomplete / parse_error / root_not_col / empty_root / no_blocks) and the card offers no edit entry.

### The Artifact editor: requests and block arrangement

- The browser `artifact-edit/store.ts` keys one edit draft by `${sessionId}:${baseRevisionId}`: `originalOrder` (base-revision block ids in page order), `targetOrder` (the arrangement draft), `orderChanged`, the saved `selection` (numbered requests with their instructions), the global instruction, the open block, the drawer state and the checking/conflict status. One chat keeps several such drafts but only one active edit canvas (`activeKeys`); switching cards keeps the previous draft (`editing=false`) with its content intact. Requests, arrangement and the composer chip survive leaving edit mode.
- Every draft has a stable `requestId` (`req_` + 12 base36 characters, `crypto.getRandomValues` preferred) and an `attached` flag. One chat keeps at most 6 drafts with content (`MAX_ARTIFACT_DRAFTS`; opening beyond that returns `limit` and the card shows a cap notice) and one send attaches at most 3 (`MAX_ARTIFACT_BATCH_REQUESTS`; the rest start detached and can be attached). Closing an empty canvas draft discards it; closing a draft with content keeps it as a detached draft visible in the switcher and as a card badge.
- The editor gains a **Pending edits (N/6)** switcher (`data-dsh-iui-edit-draft-switcher`) listing every draft of the chat with content (title, revision, request summary, active marker, conflict/detached tags, attach/discard); clicking a row activates its canvas, and only the active draft's request list / arrangement / global-instruction sections render below. Inactive drafts show a card-header badge; activating a draft from the switcher or a card entry scrolls the matching card into view.
- Opening a block popover is only a draft and creates no request; saving a non-empty instruction creates the request and assigns the smallest free number (numbers become reusable after a deletion). The number belongs to the request alone and drives the request-list row, the block badge and the six-colour cycle (blue, purple, green, orange, pink, cyan for 1–6). Blocks without a request show no number, colour or **Edited** tag. Saving an empty instruction removes that block's request.
- The editor header shows **Artifact editor** and, on narrow viewports, a close-drawer button (the docked desktop rail has no expand/collapse control). The **Edit requests** list appears only when saved requests exist: the count, a right-aligned **Clear all** (clears requests only, keeping the arrangement and global instruction) and each row's number, title, instruction and edit/delete buttons.
- **Block arrangement** is always visible: the title, "· N blocks", Reset order and the hint **Drag to reorder blocks; click a block to view or add a change request.** Reset order only restores `targetOrder` to the base revision's page order and keeps every request, its number and the global instruction. The list shows every top-level block in `targetOrder`: a drag handle (pointer drag with a 4px threshold, a 2px insertion line picked from row midpoints, and one `moveBlock` call on drop; ↑/↓ and Home/End also reorder from the keyboard), a body that only locates the block (scrolls to it in the canvas and highlights it for about 900ms) without opening the popover, the kind glyph, the truncated title, the number/colour and **Edited** tag when the block has a request, and a per-row overflow menu (locate/edit/duplicate/move/delete, with delete confirmed inside the menu) that opens the popover. Hovering a row with a saved request shows an anchored card after about 180ms with the title, number, full instruction and edit/delete actions.
- The arrangement draft is previewed live in the edit canvas: `wrapProgramForBlockEditing(program, extraction, targetOrder)` reorders the real `BlockSlot` wrappers in `targetOrder`, and the toolbar shows **Previewing the target order**; the preview is edit-mode only, and the recorded revision and exports stay unchanged until Send.
- The editor's fixed order is: header → (when requests exist) Edit requests → (undoable removal notice) → Block arrangement → divider → **Global instruction (optional)** → the **Sent to the model** summary (N block change requests, block order unchanged/adjusted, global instruction provided/not provided) and note. On wide viewports (≥1180px) it is a docked right rail (no expand/collapse control); below that it collapses into a bottom drawer opened by the toolbar button **Edit requests ({count})** between 720px and 1179px; below 720px block editing is unavailable and the card or the active edit view shows a **Window too narrow** notice (minimum width plus dismiss/exit), which returns to the editor after widening. A conflict shows the **This artifact has a newer revision** banner with retry and exit; checking shows **Checking the artifact…**.
- While editing, a silent revision probe runs every 15 seconds and on window focus/visibility change (`probeArtifactRevisionStatus`); only a `conflict` answer changes the session to the conflict state (it never auto-clears a conflict), so a concurrent update surfaces as the banner before Send.
- Instructions are edited in the block popover: Escape or an outside click closes it, unsaved text asks for an inline discard confirmation first; one instruction is limited to 2,000 characters, the global instruction to 4,000 and one request to 12 content edits.

### Composer chip and model envelope

- Every attached draft with content owns one composer reference chip (per-ref upsert/remove, independent of other chips); on send each chip serializes through its own codec and the envelopes end up in the same user message. The chip label is **Edit {title} · Revision {N} · {summary}** (summary: N changes / Reorder blocks / Global instruction; the title falls back to **Artifact editor**), and one send carries at most 3 attached chips. Deleting a chip by hand only marks that draft detached (the draft is kept and never auto-reinserted; re-attach from the switcher or the card); an 800ms presence check distinguishes a user deletion from a store replacement. Before sending, the client queries the revision route to confirm the base revision is still the latest and aborts the send with a reload notice on a conflict.
- The chip reference id is deterministic (`artifact-edit:<sessionId>:<baseRevisionId>`, derived only from the draft key), so it still resolves after a page reload; when the draft no longer exists the send returns `stale` and shows `edit.errorStale` (delete the chip and reopen editing).
- The source's codec assembles an `ArtifactEditRequest` through `serializeArtifactEditRequest`: `schemaVersion: 1`, the draft's `requestId`, `artifactId`, `baseRevisionId`, `baseRevision`, optional `title`, `style`, optional `styleId`, `edits` sorted by `selectionOrder` (may be empty), the complete `targetOrder`, a client `orderChanged: true` hint only when the order actually changed, optional `globalInstruction` and the exact `program` the user saw. At least one of content edits, an order change or a global instruction is required, and `targetOrder` must contain every top-level block id of the base revision exactly once (up to 100).
- One user message may contain multiple envelopes (one V1 envelope per chip; no V2 composite envelope yet). The JSON header carries `requestId`, and the prose tells the model to pass `requestId` + `artifactId` to `edit_ui_blocks` (content edits) or `editRequestId` to `render_ui` (order-only/global-only). The envelope is `<artifact-edit-request>` + a JSON header (with `<` escaped as `\u003c`) + English editing rules + the target block list (omitted without content edits) + the target-order list + `<artifact-program>` with the original program. The rules split by request type: with content edits the model must call `edit_ui_blocks` once with a `root = Col([...])` mini program — one top-level expression per target block in request order, optional new helper statements, no redefinition of existing statements/`$state`, no whole-page return (the page is read-only context); order-only/global-only requests require one `render_ui` call with the complete program. Both require changing only the target blocks and the minimum directly related parts, keeping the recorded style, moving the root `Col`'s top-level blocks to exactly the target order without adding/removing/merging/duplicating blocks, and asking one focused question on material ambiguity.
- The sent user message collapses each envelope into its own summary chip (`artifact-edit-summary` computes each envelope's range), so a multi-artifact send shows one chip per request; the user's own surrounding text stays readable, and the chip in history is not interactive.

### Multi-card parallel editing (M3-1)

- Drafts are separated from the canvas: `activeKeys` records the active draft per chat, `editingSessionFor` returns only that draft and `draftSessionsFor` returns the switcher list; switching cards keeps the previous draft's selection/targetOrder/global instruction. The old `closeOtherEditors` semantics are gone.
- Caps and attachment: at most 6 drafts with content per chat (`MAX_ARTIFACT_DRAFTS`; opening beyond the cap returns `{ok:false, reason:'limit'}`) and at most 3 attached drafts per send (`MAX_ARTIFACT_BATCH_REQUESTS`); a new draft beyond the batch room starts detached.
- Every draft owns a stable `requestId` (`req_` + 12 base36 characters, `crypto.getRandomValues` preferred) written into its envelope; after a successful send the draft is marked submitted, its chip is released, and the next edit creates a fresh `requestId`.
- Host v1 is "multiple V1 envelopes + an internal batch": the observer parses envelope-by-envelope with `parseEditRequestTexts` (at most 3 envelopes per message), stores each by `requestId` in a per-session map (`requestId`/`artifactId`/`mode: block|full`/`messageId`/`createdAt`, 15-minute TTL, at most 3 pending per session, only the first request per artifact accepted); a legacy envelope without `requestId` gets a generated legacy id and keeps the previous single-pending behavior; requests beyond the message cap are ignored and logged.
- Tool selection: with several pending requests, `edit_ui_blocks` needs `requestId` (an optional `artifactId` verifies ownership) and `render_ui` needs `editRequestId`; a missing selector, an unknown id or an artifactId mismatch returns a model-readable error listing the pending choices and leaves every request armed. `apply` consumes only the selected request and records its own revision; there is no cross-artifact transaction — one failure does not roll back other successful revisions.
- Differences from the external (GPT) design in v1: no V2 composite envelope (the transport stays one V1 envelope per chip); the request program is still authoritative from the envelope (registry-level program validation/digests are Phase-2 hardening); `messageId` is best-effort and turn-level reconciliation is the client-side flow in the next subsection (M3-1c); order-only requests still use `render_ui` (with `editRequestId`), zero-model execution remains future work. The shared contract also declares batch cap constants (24 block edits / 120k characters of program per batch) that are not enforced yet — Phase-2 hardening.

### Reconciliation (M3-1c)

- Revision meta returns `ArtifactRevisionMeta.requestId`, the request id the revision fulfilled: the Host writes the pending request's `requestId` into the lineage returned by `apply()`, and both the `render_ui` and `edit_ui_blocks` paths pass it through `OUTPUT`/`BLOCK_EDIT_OUTPUT` and `presentationMeta`; the client reads it back into `IntelligentUIProgram.requestId` (`programs.ts` `revisionLineage`/`blockEditProgram`).
- A submitted draft is not deleted immediately: `markSubmitted` sets `status: 'submitted'` and records `requestId`/`submittedAt`, keeping at most 12 unresolved submitted drafts per chat by submission time (oldest dropped). They do not appear in the switcher and no longer consume an attached slot.
- When the Turn closes (`IntelligentUICards` watches `turn.status === 'closed'`, once per Turn) the client collects the `requestId`s of that Turn's cards and calls `reconcileArtifactSubmissions` with a `turn.start.time - 5000` … `turn.end.time` send-time window: submitted drafts whose request id is in that set are deleted; the rest are restored as `status: 'ready'`, `submitFailed: true`, `attached: false`, with a fresh `requestId` and cleared `submittedAt`, keeping their content editable.
- UI: the card draft badge gains a `data-state="failed"` state with the label **Not completed; draft kept** (`edit.draftFailed`), and the editor switcher row shows an `is-failed` tag (title `edit.draftFailedHint`). Activating a draft or re-attaching it clears `submitFailed`; attach only adds the draft to the next Send — nothing is resent automatically.
- Boundaries: the Host keeps unfinished pending requests until their 15-minute TTL (Turn close does not clean them); Turn ownership relies on the send-time-window heuristic (historical Turns do not claim newer submissions; extreme clock/long-delay cases are unverified); each request records its revision independently (no cross-artifact transaction), so "partial success" is a normal path; the real-model partial-success path has not been GUI-validated (E2E simulates Turn close/partial completion via the harness; the real GUI covered single- and two-card success paths).

### Branch editing from an older revision (M3-2)

- The envelope JSON header gains an optional `branch: true` (`ArtifactEditRequest.branch`, with an added "this is a branch edit" prose line; old clients that omit it keep the normal edit path). On an outdated revision's conflict banner the client offers **Create a new revision from this one** (`data-dsh-iui-edit-branch`): `enableBranch` applies only when `status === 'conflict'` and `latestRevision` is known, sets `branch: true`, returns the draft to `ready`, and replaces the conflict banner with an informational note (`data-dsh-iui-edit-branch-note`, `edit.branchBannerTitle`/`Body`, showing the base revision and the known latest); the composer chip label appends ** · branch** (`edit.chip.branchSuffix`).
- A branch draft is no longer blocked by the client-side head mismatch: sending still probes the revision, but a `conflict` only blocks sends when `branch !== true`; serialization includes `branch: true` with the old `baseRevisionId`. Closing/reopening the draft keeps branch mode; a successful send clears it in `markSubmitted`. A branch draft that fails and is restored by Turn-close reconciliation loses the marker and must be re-enabled from the conflict banner (known boundary).
- The Host relaxes the latest check for branch requests in both `describeProblem` and `apply`: a recorded base must belong to the same artifact and match `record.revision === request.baseRevision`; an unrecorded base is accepted only when `baseRevision === 1` (the original render is not recorded); otherwise it returns a model-readable error without consuming the pending request. The new revision number is the artifact's current `latest.revision + 1` (`baseRevision + 1` when no head is recorded) and `baseRevisionId` points at the chosen old revision; deterministic `targetOrder` normalization, preservation warnings and `requestId` meta are unchanged; revisions above 100,000 are rejected. The non-branch path keeps the strict latest check and its messages.
- Limits: a branch makes the "latest revision" and a card's displayed revision diverge (the branch note explains it); the real-model "branch partial failure" path is not separately validated.

### Zero-model restore and local revision cards (M3-2)

- Host restore route: an exact **`POST /api/intelligent-ui/artifact-restore`** is registered under the same authentication/`effect`/dispose as the revision probe (one disposer for both; the GET behavior is unchanged). The `ArtifactRestoreRequest` body (`schemaVersion: 1`, `artifactId`, `sourceRevisionId`, `program`) requires `content-type: application/json`, at most 300 KiB and a 15-second read timeout, and is validated by `describeArtifactRestoreProblem`; the source must exist in the registry (404 `source_missing`), belong to the same artifact (400 `artifact_mismatch`), and not be the latest revision (409 `already_latest`); the program must parse with a `Col` root (400 `invalid_program`); revisions above 100,000 return 400 `revision_limit`; non-POST methods return 405 `method_not_allowed`. Errors use `{error:{code,message}}` with 400/404/409/413/405 statuses and `no-store`.
- Success returns **201** `{ok:true, revision:{artifactId, revisionId, baseRevisionId, revision, program, title?, style, styleId?}}`. The record uses `revision = latest + 1`, `revisionId = restore_<16 hex>` (8 random bytes, up to 8 collision retries), `baseRevisionId = sourceRevisionId`, `sessionId = "local-restore"`, copies the source `style`/`styleId`/`title`, and does not store the program in the registry. No model call is involved.
- Client `src/client/artifact-edit/local-revisions.ts`: a card shows **Restore as new revision** (`data-dsh-iui-restore`) only when the GET probe reports a conflict (i.e. not the latest revision; the latest card and `localRevision` cards never show it); clicking POSTs the restore. The returned revision is stored as a `LocalArtifactRevision` in **`localStorage`** (key `dsh-intelligent-ui-local-revisions:v1:<sessionId>`, at most 20 per chat, deduplicated/replaced by `revisionId`, oldest evicted by `createdAt`) and converted by `localRevisionProgram()` for rendering (`localRevision: true`, `artifactId`/`revisionId`/`baseRevisionId`/`revision`, `style`/`styleId`, still editable). Local cards render filtered by `turn` (the Turn that triggered the restore) exactly once in that Turn's card list; `IntelligentUICards` merges local cards with tool-result cards via `useLocalRevisions`.
- Limits: local cards exist only in browser-local storage — clearing storage or switching devices loses them; they never become assistant message entries and do not participate in the export, image-export or replay chain (which only accept tool-result/meta cards); restore is unavailable for the latest revision; local cards render in the Turn that triggered the restore, not at the bottom of the conversation; the real-model "branch partial failure" path is not separately validated.

### Draft persistence (M3-3a)

- `store.ts` writes unsent drafts per browser tab to `sessionStorage`: one record per draft under `dsh-iui-edit-draft:v1:<sessionId>:<baseRevisionId>` plus a per-chat index under `dsh-iui-edit-draft-index:v1:<sessionId>`. Only restore-relevant fields are stored (`key`/`sessionId`/`artifactId`/`baseRevisionId`/`baseRevision`/`requestId`/optional `title`/`style`/optional `styleId`/`program`/`originalOrder`/`targetOrder`/`orderChanged`/`selection` (`blockId`/`order`/`instruction`)/`globalInstruction`/`attached`); blocks and the wrapped program are recomputed on restore via `blocksForProgram`/`wrapProgramForBlockEditing`, and transient UI state (open block, draft text, editor state) is never persisted.
- Writes are debounced by 250 ms (`DRAFT_PERSIST_DELAY`) and skipped when the payload is unchanged; the per-chat index is capped at 6 drafts, oldest persisted entry first. Discard, a successful send, reconciliation-deletion and empty-prune remove both the record and its index entry; quota/JSON/restricted-context failures stay silent (best effort).
- Lazy restore APIs: `ensureArtifactDraft(key)` (idempotent; an in-memory draft always wins; corrupt/unusable records are deleted), `hydrateArtifactDrafts(sessionId)` (restores every indexed draft) and `flushArtifactDraftPersistence()` (flushes debounced writes for tests/page lifecycle). `editSessionFor`, `useArtifactEditSession` (hydrates in a mount `useEffect`, never during render), `serializeArtifactEditRequest` (resolves a deterministic chip reference back to its key), `draftSessionsFor`, `activeDraftKeyFor` and `activateDraft` trigger restore when the memory store is empty.
- A restored draft comes back with `status: 'ready'`, `editing: false`, its `requestId`/`attached` kept, selection filtered to surviving `blockId`s, `targetOrder` re-validated as a complete permutation (an invalid record is discarded) and the global instruction truncated to 4,000; references are rebuilt and the composer chip re-syncs within 250 ms, so a restored chip can be sent again.
- Limits: `sessionStorage` is per-tab — a reload keeps drafts but **other tabs never see them**; `branch`/`latestRevision`/`submitFailed` and the undo record are not persisted (branch must be re-enabled from the conflict banner); programs above the 200,000-character cap are not persisted; there is no automatic `pagehide` flush (only the exported flush function).

### Cross-tab soft lease (M3-3b)

- New `src/client/artifact-edit/tabs.ts`: `BroadcastChannel('dsh-iui-artifact-edit-tabs:v1')` with `lease`/`release`/`query` messages; a lease is `{tabId, expiresAt}` with a 30-second TTL (`LEASE_TTL_MS`) renewed every 10 seconds (`RENEW_MS`); `tabId` prefers `crypto.randomUUID()`. When the channel is unavailable (`BroadcastChannel` undefined or construction throws) initialization is a no-op, so every API degrades to local/no-notice.
- `ArtifactEditView` queries other tabs when the edit canvas opens (`session.editing`), claims the lease 400 ms later only when no foreign lease exists, renews it every 10 seconds, and clears the timers plus releases the lease on close/unmount. A foreign lease renders a banner (`data-dsh-iui-edit-lease-conflict`, title/body/**Take over editing** button `data-dsh-iui-edit-lease-takeover`); activating it calls `claimEditLease(key, true)` as a forced takeover — the claiming tab's banner disappears and the previous owner receives the lease and shows the banner instead; expired leases are lazily pruned by `activeLease`.
- Limits: the lease is advisory only — it never merges changes and never blocks editing; it covers the revision being edited, not every unsent change in a draft; takeover only moves the notice and does not revert the other tab's unsent work; an unavailable channel means the notice is silently absent; the Host revision check remains the final authority; extreme concurrency/clock skew is unverified.

### Temporary-style block editing (M3-4)

- Contract: `ArtifactEditRequest.temporaryStyle?: StyleSnapshot` and `ArtifactRevisionMeta.temporaryStyle?`, validated by `isStyleSnapshot`, `baseLayout === style`, never combined with `styleId`, and at most 20,000 JSON characters. The envelope header carries the snapshot, and the content-edit prose tells the model the Host reuses it and that no style/styleId arguments go to `edit_ui_blocks`.
- Client: `supportsBlockEditing` accepts a `styleSource === 'temporary'` card only with a valid snapshot (still non-running, extractable and wrappable); the edit session stores `temporaryStyle`/`style` (empty `styleId`). A serialized content-edit request carries `temporaryStyle` and no `styleId`; a temporary-style request with only a reorder/global instruction returns `{ok:false, problem:'temporary_order'}` before the probe → `edit.errorTemporaryOrder` (the draft is not consumed); content+reorder mixes stay allowed and the Host reorders deterministically. The draft-persistence payload may carry the snapshot (validated on restore, ≤20k), `programs.ts` reads `temporaryStyle`/`styleSource:'temporary'` back from the revision meta, and local restore cards copy it too.
- Host: `ArtifactRevisionRecord` gains optional `temporaryStyle` (`isStyleSnapshot` + `baseLayout === style` + JSON ≤ 20,000; old registry files stay readable); `edit_ui_blocks`'s output schema/value and output meta plus `presentationMeta`/lineage pass the snapshot through with `style = snapshot.baseLayout` and no `styleId`. The `render_ui` full-program fallback stays closed for temporary styles and returns a dedicated error: `render_ui: this artifact uses a result-owned temporary style, so only content edits through edit_ui_blocks are supported. Order-only or global-only edits on a temporary style are not supported; ask the user to edit the page content, or re-render it with a saved style first.` The restore route copies `source.temporaryStyle` into the new record and the response's `revision.temporaryStyle`.
- Limits: temporary-style results support block content edits and natural-language style edits (B1); order-only/global-only requests remain unsupported (blocked by the client and rejected by the Host `render_ui` fallback) and need a saved/built-in style; a temporary card without a valid snapshot is not editable; the real-model/real-GUI path is recorded in the B1 verification entry (E2E plus one real-GUI smoke).

### Natural-language style editing inside the editor (B1, 2026-11-08)

- **Request contract**: `ArtifactEditRequest` is now a discriminated union — the block variant keeps the legacy header and program body compatible (its prose is now generated by `blockEditToolContract`, so the whole text is no longer guaranteed byte-identical); a new `kind: 'style'` variant requires `requestId`, `style` (the recorded layout, which the revision must keep), `styleInstruction` (1–2000 chars) and the complete base `program`, with optional `title`/base `styleId`/base `temporaryStyle`/`branch`. The style variant forbids `edits`/`additions`/`targetOrder`/`orderByParent`/`orderChanged`/`strict`/`globalInstruction` (cross-field => `unknown_field`), and a block envelope carrying `styleInstruction` is rejected too. Serialization keeps the block envelope header and program body compatible; the `Tool-call contract:` line is generated by the helpers while the remaining explanatory prose is still hand-written; the prose tells the model to call `render_ui` exactly once with `editRequestId`, the complete program, the recorded layout and a complete `temporaryStyle` (omitting `styleId`), and warns that the Host only reports content changes as warnings. Block- and style-envelope tool arguments are not kept aligned by hand-written prose: `blockEditToolContract`/`buildBlockEditToolArgs` and `styleEditToolContract`/`buildStyleEditToolArgs` are single contract sources, the serializers generate a `Tool-call contract:` line from them, and Host coupling tests execute the helper-produced arguments (block fragments/render and style builtin/saved/temporary), so drift on either side fails the suite; the branch instruction line is likewise single-sourced through `branchEnvelopeLine`.
- **Host authorization and minting**: style requests must carry an explicit `editRequestId` (a single pending style request is never auto-applied by a selector-less `render_ui`, H1); `render_ui` performs a side-effect-free peek after the enabled check (H2) before on-demand authorization; a bound on-demand operation rejects the style apply (H3, avoiding a double result-snapshot write for one callId); the style edit records the model-returned `temporaryStyle` (H7) and shares one `validateTemporaryStyleSnapshot` with on-demand (schema / `baseLayout === style` / contrast). The revision records `style` + the model snapshot with no `styleId`/`editedBlockIds`; an unchanged program + snapshot is a no-op that keeps the request armed; a wholesale redesign with no recognizable blocks adds one H4 preservation warning. `edit_ui_blocks` redirects style requests early and keeps them pending.
- **Snapshot boundary (root-cause fix)**: before writing a revision file, `ArtifactRevisionStore.record` records a revision's `temporaryStyle` in the ResultStore under its result id (snapshot first, revision second; failure is retryable and never leaves half state). `createArtifactRevisionStore` accepts an optional `results` sink, wired in index.ts. Temporary-style revisions from edit/restore/structure can therefore use Save as template on revision cards (previously `SaveResultAction`/the legacy footer adjust failed with `result_missing`); no backfill of old records.
- **History and compatibility**: no new durable revision fields or `ArtifactHistorySource` values; `historySource()` uses prefixes (restore, `struct_`) and infers a temporary-style revision without `editedBlockIds` as edit (the history row already shows the temporary-style badge). `presentationMeta` carries only `style`/`temporaryStyle`/`title`, never `kind`/`styleEdit` (H6).
- **Client/UI**: a style section at the top of the edit panel (recorded skin/layout, disclosure, ≤2000-char textarea, style-revision note, clear); the instruction writes straight into the draft and blocks mixing with block/arrangement/global content (`style_mixed`); the chip and sent-message summary show "style adjustment". `ArtifactEditView`/`EditPanel` pass `styleEditSupported` through: on a new Host with an editable card the footer Adjust style fallback is hidden (Save stays); old Hosts or non-editable cards keep the footer button (redirected read-only fallback cards keep neither Save nor Adjust); when the capability is absent, persisted style instructions are cleared so an old Host never receives an unparseable envelope.
- **Model path**: render_ui tool description and the `temporaryStyle`/`editRequestId` parameter docs, ARTIFACT_EDIT_NOTE, the Agent Skill and the integration reference describe the style path (layout never changes across card/article/free; content changes are warnings; temporary style can be minted only by on-demand or a pending style request).
- **Limits**: a natural-language style edit turns a saved/built-in-style page into a result-owned temporary style (without a model theme it inherits the session theme; template-theme continuity is a follow-up); history source shows "block edit" plus the temporary-style badge; the style section is driven only by the `styleEdit` capability and card editability (a missing base registration does not hide it; applying fails instead), while old Hosts or non-editable cards keep the footer fallback (redirected read-only fallback cards keep neither); deterministic built-in/template switching is covered in the next section.
- **Verification**: new Host style mint/apply/security tests (H1/H3/H4 mutation-checked), revision-store snapshot-boundary tests, mode capability; client style envelope/mix/persistence/chip tests and E2E coverage (style section, chip, envelope fields, mocked style revision card, footer fallback/capability); final gate numbers come from the real run.

### Deterministic style switching (zero model, 2026-11-08)

- **Request contract**: the existing authenticated struct route `POST /api/intelligent-ui/artifact-structure` gains a request-level `targetStyle` (discriminated union: `{kind:'builtin', layout:'card'|'article'}` or `{kind:'template', styleId:'cs_…'}`) and `sessionStyleScope` (the resolution scope for session templates, a selector rather than authorization). Single-intent rule: with `targetStyle`, `operations` must be empty (`style_with_operations`) and `preview` is unsupported (`preview_not_supported`); without a target the previous non-empty-operations semantics stay. Targets are durable identities only — built-in layouts or visible saved templates; no client snapshot/directives/theme is ever accepted, and built-in `free` is rejected (free only through a saved free template).
- **Host execution**: the target identity is resolved Host-side (builtin → layout; template → `styles.resolve(styleId, sessionStyleScope)`, invisible/deleted → 404 `style_missing`); an Article target reuses the exact Toc/Section + anchor predicate render_ui uses (now `src/shared/article-layout.ts::describeArticleLayoutProblem`, shared by the Host and the client) → 400 `article_unavailable`; when recording, for a base that already has a revision record (revision ≥ 2) the client's claimed base `style`/`styleId` must match the authoritative record (otherwise 409 `base_style_mismatch`, nothing written — applied to those struct requests, fixing the previous body-identity trust); the initial revision 1 has no stored record, so its identity still comes from the request/registration. A base without a temporary snapshot whose identity already equals the target → 400 `no_change`; a temporary-style base with any durable target is always a change (the snapshot is dropped). On success the program is **byte-identical** to the base, `style`/`styleId` come from the resolved target, no `temporaryStyle`/`editedBlockIds` are written, and the `struct_` revision id, `latest+1`, branch, idempotency ledger, program registry and response shape are unchanged.
- **History/compatibility**: no new durable revision fields or `ArtifactHistorySource` values. A `struct_` revision without `editedBlockIds` is the deterministic style-switch signal: the Host still reports source `structure` (old clients show "structure operation" and restore/branch normally), while new clients label it as a style switch using that convention. Old Host + new client: the missing capability hides the picker; new Host + old client: nothing visible changes.
- **Client/UI**: the edit-panel style section adds a "Switch style" single-intent radio picker; targets are shown as two labeled groups with a divider — Built-in styles and Saved styles — inside one mutually exclusive radiogroup (built-in Card/Article; saved templates with swatches and layout). ### Hierarchical ordering (M4-2)

- Contract: `ArtifactEditRequest.orderByParent?: Record<'root' | CST nodeId, readonly nodeId[]>`, projected into the envelope header; shared shape validation (`invalid_order_by_parent`: keys are `root` or `n\d+`, each group non-empty and ≤100, ids deduplicated, at most 61 groups). A value contains a complete permutation of that parent's **editable children** only; the client sends only changed groups; `targetOrder` remains the base root order.
- Host validation: `describeOrderByParentProblem` checks against the base CST tree — parent exists, is not `@Each`-scoped, not a shared named expression, not opaque and has a children slot; every group must be a complete permutation of the editable children, with unknown/duplicate/cross-parent ids rejected; `orderByParent.root` must not disagree with legacy `targetOrder` (which must be the base root order); a subtree being content-edited by the same request cannot be reordered (ancestor/descendant conflict); no-op groups are ignored. Failures are model-readable, keep the request armed and write no revision.

The `render_ui` full-program path and the `edit_ui_blocks` nested-content path share `apply`; an order-only request (`edits: []` + `orderByParent`) is accepted, records the normalized program in the revision and returns it in the result meta/`presentationMeta`; `editedBlockIds` is `[]` for order-only and the affected root block ids for nested content plus order.

In nested mode `EditPanel` adds a **Nested block order** section: one title per parent with indented rows (global numbering, edit tag, pencil, locate-on-body), same-parent pointer drag (cross-group drags are rejected) plus grip/keyboard ↑/↓/Home/End, and **Reset nested order**; hooks: `data-dsh-iui-edit-nested-arrangement/-group/-list/-row/-grip/-body/-edit/-reset-nested`.
- Limits: nested ordering is still opt-in and not persisted; there is no live canvas preview (the list shows the target order); no cross-container moves; order-only requests still cost one model `render_ui` turn (not zero-model); a parent subtree being reordered must not be content-edited in the same request; the Host still uses the envelope program as its base (authoritative program store remains M4-3); `editedBlockIds` is `[]` for order-only requests.

### Deterministic structure operations (M4-3)

- Authoritative program registry: `src/host/artifact-structure.ts::createArtifactProgramStore` persists `<DSH_HOME>/dsh-intelligent-ui-programs.json` (`{version, programs[]}`): at most **200** records / **50 MB** of program text, LRU-evicted by `lastAccess`, atomic write, corrupt recovery to empty. It records the program of every successful `render_ui`, `edit_ui_blocks`, structure-route and restore revision. `lookup(artifactId, revisionId)` is the **only** accepted base for structure operations; a client-supplied `program` field is rejected as `unknown_field`.
- Idempotency ledger: `createArtifactStructureOperationStore` persists `<DSH_HOME>/dsh-intelligent-ui-structure-operations.json` (at most 200 records; `operationId` plus a canonical request digest -> result lineage). A replay with the same `operationId` and body returns the recorded result (HTTP 200); the same id with a different body returns 409 `operation_replayed`.
- Route: the authenticated exact **`POST /api/intelligent-ui/artifact-structure`** (auth as restore; JSON body ≤64 KiB; success 201 `{ok:true, result: ArtifactStructureResult}`; replay 200). It validates that the base exists in the authoritative registry, applies latest/branch rules, and uses `buildArtifactTree` to validate `nodeId`/`sourceDigest`/scoped(`@Each`)/shared/opaque/root targets and `toIndex` bounds. The operation set is `delete`/`duplicate`/`move` plus M4-6 `props` (Divider/Spacer quick adjust: validate the bag against the node component and rewrite the named statement body through `replaceNodeContent`); a batch (at most 20 operations) is applied atomically in request order against an evolving tree, then re-parsed and re-validated. On success it records `revision = latest + 1` (a branch on an old base also gets `latest + 1`), inherits `style`/`styleId`/`temporaryStyle`/`title`, puts the affected root ids in `editedBlockIds`, and stores the new program in the registry. Error codes: 400 `invalid_input`/`operation_conflict`/`program_invalid`, 404 `artifact_missing`/`base_missing`, 409 `base_not_latest`/`operation_replayed`, 500 `storage`, 405/413.
- Index semantics: `duplicate.toIndex` is the final insertion position among that parent's **editable children** (chrome excluded); `move.toIndex` is the final 0-based editable index after removal.
- Client: the shared `src/shared/artifact-structure.ts` defines the route, request/operation/result types, `describeStructureRequestProblem`, `isArtifactStructureResult` and `MAX_ARTIFACT_STRUCTURE_OPERATIONS = 20`. Structural operations now run the queue → total-preview → Apply pipeline described in the edit-pipeline section: `applyEditRound` submits the queue as one atomic batch, records a local `kind:'structure'` revision card (rendered in the Turn that triggered the operation, labelled **Structural revision**) and rebases the draft; only a pure-structure Apply calls `markSubmitted` to close the editor, while a mixed Apply keeps the rebased draft and auto-sends. The earlier single-operation `applyArtifactStructure(key, blockId, 'delete'|'duplicate', turn)` helper that applied and closed the draft immediately has been removed; the paragraph above describes history only. `IntelligentUIProgram.localRevisionKind` distinguishes restore/structure/props cards, and local-revision validation/persistence stays compatible with old restore records.
- UI: arrangement rows (root and nested) expose hover/focus **Duplicate** (immediate) and **Delete** (two-step inline confirm, 3 s, danger styling, no `window.confirm`/`alert`); `structureBusy` disables the actions with a status, and `structureError` is a dismissible `role=alert` that auto-hides after 8 s; hooks: `data-dsh-iui-edit-structure-duplicate`/`data-dsh-iui-edit-structure-delete`, `data-confirming`, `data-structure-confirming`, `data-dsh-iui-edit-structure-error`/`-dismiss`/`-busy`.
- Limits: the UI exposes delete/duplicate only (the Host has a same-parent move API but no move UI; cross-container moves are not implemented); the registry only covers registered revisions still inside the 200/50 MB LRU — a legacy card registers automatically the first time the client uses authoritative state (see "Artifact authoritative-state lifecycle and base registration"), and unregistered or evicted bases still return `base_missing` and need a re-render; `branch` also requires the base program to be present; local structure cards are localStorage-only and render only in the triggering Turn (no assistant message/export/cross-device, no lost-card prompt yet); no diff preview or multi-step undo; delete leaves helper declarations (no GC); `Section`/`Toc`/`@Each`/shared expressions are limited by CST rules; (Historical: at M4-3 structure operations and content edits could not be mixed in one action, and a structure operation directly `markSubmitted` the current draft; the 2026-11-10 edit pipeline replaces that behaviour — see below.)

### Artifact authoritative-state lifecycle and base registration (2026-11-07)

- **Root cause**: block editing depends on Host-side collaborative state (the authoritative program registry, revision registry and structure ledger), but a card rendered before that state existed has no registration path, so the same old card surfaces differently across structure operations, revision history and restore (`artifact_missing`/`base_missing`, empty history, `source_missing`). This increment adds the one "rendered content → Host authoritative state" lifecycle and a unified base resolve/failure boundary. There is no backfill and no background migration.
- **Initial revision identity**: the first `render_ui` tool call id is both the artifactId and revision 1's revisionId, i.e. `revisionId === artifactId`; revision 1 exists only in the authoritative program registry and **writes no revision record**, so recorded revisions start at 2. `src/shared/artifact-edit.ts::isInitialRevisionId(artifactId, revisionId)` is the single predicate used by base registration (initial anchor) and the structure route's base resolution; the restore route keeps its original program-only fallback (a missing source record is accepted when its authoritative program is still retained, without an extra initial-identity check).
- **States and transition**: `rendered` (only card content, no Host state) → `registered` (that revision has an authoritative program). Structure operations, history and restore require `registered`. One registration covers both provenance shapes: the initial anchor (`revisionId === artifactId`, no record needed) and the recorded anchor (`revisions.get(revisionId)` exists and `record.artifactId === artifactId`, for a recorded revision whose program was LRU-evicted). Neither → 404 `unknown_revision`.
- **Write-once**: registration only fills a missing program and never overwrites; an already registered revision with a byte-identical program → 200 `{ok:true,registered:false}`; a different program → 409 `program_conflict`. Registration **writes no revision record** (revision 1 stays program-only) and a failure writes nothing.
- **Route contract**: the authenticated exact `POST /api/intelligent-ui/artifact-base` (same `connection.requestRejection` gate as restore, which runs before method dispatch), body `{schemaVersion:1, artifactId, revisionId, program}` with a strict whitelist (only those four keys), reusing `ARTIFACT_ID_PATTERN` and the shared bounded-text rule (non-empty, at most 200,000 characters, same control-character rule; the helper is exported from `artifact-edit.ts` so the rules cannot drift). The body is capped at **1 MiB** (a 200k multi-byte program can exceed 300 KiB) with JSON plus a 15 s read timeout, and the structural check requires `extractArtifactBlocks(program).rootType === 'Col'`. Success is 200 `{ok:true,registered}` with `no-store`; errors are `{error:{code,message}}`: 400 `invalid_input`/`invalid_program`, 404 `unknown_revision`, 409 `program_conflict`, 413 `payload_too_large`, 500 `storage`, 405 `method_not_allowed`, and errors never echo the program.
- **Base resolve boundary**: `src/host/artifact-base.ts::resolveArtifactBase({revisions,programs},{artifactId,baseRevisionId})` extracts the structure route's latest/firstProgram/baseProgram judgment (empty artifact → `artifact_missing`; known artifact with a missing base program → `base_missing`). The structure route keeps its latest/branch rules, CST validation, revision recording and exact error text unchanged.
- **Client ensure**: `src/client/artifact-edit/artifact-base.ts::ensureArtifactBase({artifactId,revisionId,program})` is the single entry point (no A/B split), single-flighted and permanently cached by `artifactId\0revisionId`. A success caches `present`/`registered`; an old Host without the route (404) caches the `unsupported` capability so that revision is never probed again; network/other non-2xx answers return `failed`, are not cached, are retryable and never throw or show a user-visible error. Trigger points: opening the edit canvas (new, retained and submitted-reused drafts, fire-and-forget), awaiting before structure preview and apply POSTs, and awaiting before loading the revision-history dialog and before restore sends. `unsupported`/`failed` never block an operation; it proceeds on the non-authoritative path. Model-facing behavior and old-card content are unchanged.
- **Unified failure semantics**: the store's `structureFailureMessage({code, surface, failureKey})` serves preview, apply and quick adjust (props); preview now parses the response body's `error.code` too (previously only apply did). `artifact_missing`/`base_missing` always map to actionable copy (authoritative program registration incomplete or record evicted; card record missing; close/reopen, re-render, instruction editing) instead of a generic "try again" dead end; `base_not_latest`/`no_change` keep their existing mapping.
- **Trust position**: a client-supplied program has the same trust level as the existing edit envelope / restore path (registration only; write-once + current-revision-only + structural validation). The structure route still reads only the authoritative program, never trusts a client program, and structure requests never carry a program.
- **Accepted deviations (documented, not fixed)**: a registered initial revision's `createdAt` becomes the registration time; old cards untouched by any authoritative operation stay unregistered (no backfill); an LRU-evicted non-current revision program cannot be reconstructed client-side.
- **Mixed deployment with an old Host**: when the registration route answers 404 the client caches `unsupported` and degrades to non-authoritative paths — quick adjust falls back to instruction editing, structure operations explain the missing authoritative program actionably, and re-rendering restores the page.
- **Verification**: `test/host/artifact-base.test.mjs` (14 tests: route registration/disposer, auth before method dispatch, POST-only/content-type/bad JSON/>1 MiB, field and program validation, initial-anchor registration and write-once conflict, unknown revision and a record from another artifact, recorded anchor unlocking structure/history/restore, a no-model end-to-end upgrade — register → preview → apply 201 revision 2 → history with the initial revision and revision 2 → restore the initial revision 201 revision 3 — structure error-semantics regression, plus review follow-ups: failed program-store write leaves no phantom record, padded over-limit program is 400, and a retained-program non-initial restore keeps the old fallback); `test/client/artifact-base.test.mjs` (7 tests: single flight, success cache, 404 unsupported capability cache, retryable network failure, retryable malformed 200, invalidation re-posts, invalidation during single flight cannot repopulate); `test/client/artifact-edit.test.mjs` gains 4 tests (opening the editor registers once with the card identity, structure preview awaits registration first and carries no program, preview+apply+props share the missing-base copy, success→miss→reopen re-posts); browser `artifact-edit` scenario 36 (legacy card registers with its authoritative identity, registration precedes structure requests, old-Host 404 degradation, actionable preview/props copy, semantic artifact/status/sequence assertions), suite **519 checks**.

### Auto-fit chat content width while editing (user-feedback fix, second round)

- Entering edit mode (mounting the docked panel) narrows the main chat content so the right rail cannot overlap it, and exiting restores the user's previous width. The shell's width preference is never modified; only the conversation content element's inline `--dsh-chat-content-width` is temporarily overridden.
- Second-round root cause: the first version computed against the **viewport center**, ignoring the sidebar and conversation column (which can start after the sidebar); it also used `parseFloat` on a `clamp(...)` custom-property token, failed, and fell back to 748 instead of the real width (e.g. 920), so the panel still covered content.
- Pure function `fitChatContentWidth` (`src/client/artifact-edit/panel-width.ts`): optional `columnLeft`/`columnWidth` (defaults 0/viewportWidth preserve the old results); `panelWidth = clamp((viewportWidth - current) / 2 + 16, 272, 360)`, `panelLeft = viewportWidth - panelWidth`, `maxContent = 2 * (panelLeft - gap - columnLeft) - columnWidth`, `desired = min(current, maxContent)`, iterated to a fixed point (at most 8 rounds, <0.5 px converged); `minContent = 360`; returns the original value when the viewport is too small or the preferred width already fits.
- DOM helper `applyEditChatContentWidth`: active only when `matchMedia('(min-width: 1180px)')` matches and `[data-conversation-content][data-conversation-region="chat"]` exists; saves the original inline value and priority. The content width is read from the content parent's `--dsh-chat-user-width` (user preference) when present, otherwise via a hidden probe (`width: var(--dsh-chat-content-width)` inserted and measured with `getBoundingClientRect()`), which resolves `clamp()` values to real pixels. `columnLeft`/`columnWidth` come from the content element's `getBoundingClientRect()` (the conversation column after the sidebar). It recomputes on `resize` and through a `MutationObserver` on the content parent's and element's `style`, so dragging the shell width handle while editing refits immediately; a `writing` flag ignores its own writes to avoid a feedback loop; below the breakpoint or when already fitting it restores the inline value; cleanup restores/removes the inline override, disconnects the observer and leaves the user preference untouched. `EditPanel` calls it from a single mount/unmount `useEffect` and never reads the DOM during render.
- Real GUI (ego, latest isolated build, 1800×1000, sidebar 280 / conversation column left=280 width=1520): opening the editor sets the inline content width to **752px**; the chat card's right edge is 1412.5 and the Exit editing button's right edge is 1382.5 against a panel left edge of 1440, so the button is visible and unobstructed; setting the user width preference to 1600 while editing keeps 752px without overlap; exiting removes the inline override and the parent's 1600px preference remains.
- Deployment: client-plugin changes only take effect after **restarting `dsh-web`** (a page refresh is not enough). The user's main GUI once showed old behavior because it was still running an older client bundle; when docs and behavior disagree, check the service restart first.
- Limits: only the ≥1180px docked mode is affected; the panel CSS clamp still uses the 748 fallback; if the shell ever relocates `--dsh-chat-content-width`/`--dsh-chat-user-width` or the `data-conversation-*` attributes, the centralized selector/variable constants must be updated.
- Tests: `test/client/panel-width.test.mjs` (14 tests: fixed point, default viewport, wide viewport, breakpoint, already fitting, too-small viewport, minContent, common viewports no overlap, invalid sizes, column-aware sidebar offset); the browser `artifact-edit` suite at 519 checks includes auto-fit/restore, following the user width dynamically, the real 1180px shell fit, the row menu/input orbit and the absent expand button.

### Block-fragment editing (Phase 1)

- `src/shared/artifact-block-bundle.ts` provides pure slicing and splicing. `extractBlockBundle(program, blockIds)` returns the selected blocks' expression sources (a bare statement reference resolves to its right-hand side), the transitive `frozenStatements` they depend on (read-only source), the `stateSources` (`$name = ...` declarations) and an `outline` of every top-level block, with `statementId` and title.
- `spliceBlockBundle(baseProgram, blockIds, fragmentProgram)` parses the model's mini program and requires a root `Col` with exactly one direct child per selected block; it replaces only those root-child slots in `blockIds` order while every other root child, root tail argument and base statement stays byte-identical. Non-root fragment statements become appended helper statements; a name collision with a base statement/`$state`, a duplicate or unknown block id, a count mismatch or an identifier that would not exist after composition returns a retryable error. The composed page is re-parsed and re-recognized and must keep the same number of top-level blocks.
- The Host adds the `edit_ui_blocks` tool (registered before `render_ui`; `mode.ts` denies both tools for disabled sessions and execute also guards on enablement). It only accepts a pending edit request and, with several pending, selects exactly one by `requestId`/`artifactId`; with empty `edits` (order-only/global-only) it asks for `render_ui` instead (and names the `editRequestId` to pass); otherwise it slices, splices, applies the deterministic `targetOrder` reorder and preservation warnings, records `revision = baseRevision + 1` and consumes the request. Its canonical value/result meta is `{artifactId, revisionId, requestId?, baseRevisionId, revision, editedBlockIds, program, title?, style, styleId?, temporaryStyle?}`; `presentationMeta` always carries the composed `program` (the tool returns only fragments), and the client's `programs.ts::blockEditProgram` builds the revision card from it. `edit_ui_blocks` process rows reuse the compact `RenderUiRow`.
- `render_ui` fallback split: with several pending requests it selects one by `editRequestId`; a pending request with content edits makes `render_ui` throw a readable "call edit_ui_blocks" error while keeping the request armed; order-only/global-only requests keep the full-program path (style/temporary-style/conflict checks unchanged).
- Phase 1 still sends the full page in the envelope as read-only context; the gain is the byte-identical unselected source and the composition/validation guarantee. Input-token savings (Host program cache / client context route) are deferred to Phase 2.

### Edit robustness (M1)

- A failed `render_ui` / `edit_ui_blocks` tool row shows one readable reason in its collapsed state: the recorded result text first, then the structured error reason, then `name: code`; whitespace is collapsed, the detail is at most 160 characters, the full text sits in the title, and the tool arguments are never read (`RenderUiRow.tsx`).
- The silent revision probe only raises the conflict state (never auto-clears a conflict) and never touches the popover/draft state, so a concurrent update surfaces as the conflict banner before Send.

### Host validation, deterministic reordering and revision lineage

- `host/artifact-edit.ts` prepends a `session/event` listener for `user/message`, handles only real user messages (injected skill/file context with `source.kind !== 'user'` does not count) and parses every envelope with `parseEditRequestTexts` (at most 3 per message). Beyond the existing checks it requires `targetOrder` to be a complete permutation of the base revision's top-level block ids (`describeTargetOrderProblem`: wrong_length / unknown_block / duplicate_block / missing_block), allows empty `edits`, and rejects a request that changes nothing (no edits, same order, no global instruction). A failed validation keeps an `invalidReason` entry (the tool call returns it); valid requests enter a per-session map keyed by `requestId` (`requestId`/`artifactId`/`mode`/`messageId`/`createdAt`): 15-minute TTL, at most 3 pending per session, at most 64 sessions, only the first request per artifact per message armed (duplicates carry an `invalidReason`), and a legacy envelope without `requestId` keeps the previous single-pending path. A turn that calls no tool leaves them pending; a later message replaces/adds by `requestId`.
- `pending(sessionId, selector)` returns the single request when there is exactly one and no selector; with several pending and no selector it returns `multiple_pending`, which the tool layer turns into a model-readable error listing the pending `requestId`/`artifactId` values (`listPending` provides the list). Both tools share `artifactEdits.apply` with different inputs: `edit_ui_blocks` passes the page composed by `spliceBlockBundle` as `composedProgram` (skipping `render_ui`'s styleId/temporaryStyle argument checks; the recorded request style always wins), while `render_ui` applies a pending edit only after every ordinary validation and, when the request has content edits, first throws "call edit_ui_blocks" while leaving the request armed. Both consume only the selected request (every other pending request stays armed) and reject an expired/unreadable/missing request, a stale base revision, an updated program whose root is not `Col`, and a composed/updated program that no longer re-recognizes the same top-level block set; each request is validated and recorded independently (no cross-artifact transaction). The Host does not trust the client's `orderChanged` hint: it compares the base block-id order with `targetOrder` itself and, when the order changed, deterministically reorders the program's root `Col` children through `reorderProgramToTargetOrder` — mapping updated blocks to base blocks by statement name, then title plus component type, then a unique title, mapping updated blocks back by statement name, then title plus component type, then a per-type page-order fallback, and reordering the root children. When a one-to-one mapping is impossible it throws a retryable error without consuming the request, and a normalized program above 200,000 characters is rejected. On success it computes preservation warnings for unselected blocks (at most 6), records the new revision (`revision = baseRevision + 1`, `revisionId = current tool callId`) and consumes that request.
- `render_ui`'s success value gains optional `artifactId`, `revisionId`, `requestId`, `baseRevisionId`, `revision`, `editedBlockIds`, `program`, `styleEdit`, `temporaryStyle` and `title` (for edits); `edit_ui_blocks`'s fixed output is `{statements, style, styleId?, title?, warnings?, artifactId, revisionId, requestId?, baseRevisionId, revision, editedBlockIds, program}`. `presentationMeta` returns `null` for ordinary renders and the lineage object (including the fulfilled `requestId`, plus `temporaryStyle` for temporary-style edits) for edits — `edit_ui_blocks` always carries the composed `program` plus the recorded style/title. The client's `programs.ts` overrides the program used for rendering, replay and further editing with `presentationMeta.program`, `blockEditProgram` builds the revision card from the `edit_ui_blocks` meta (`program`/`title`/`style`/`styleId` + lineage), and both read `requestId` into `IntelligentUIProgram.requestId` for Turn-close reconciliation; both show the revision number on the card history icon. An order-only result reads `Interactive UI updated for the user (revision N of the artifact, block order adjusted).`; a content edit (including `edit_ui_blocks`) reads `Interactive UI updated for the user (revision N of the artifact, K blocks edited).`; the ordinary result line is unchanged.
- `artifact-revisions.ts` keeps its storage and route: revision records are written atomically to `<DSH_HOME>/dsh-intelligent-ui-artifacts.json` (`{version: 1, revisions: [...]}`) with `revisionId`, `artifactId`, optional `baseRevisionId`, `revision`, `sessionId`, `style`, optional `styleId`/`temporaryStyle`/`title`/`editedBlockIds` (an empty array for order-only updates) and `createdAt`. It retains at most 400 records (oldest `createdAt` dropped), records are immutable, reads return clones, a corrupt file is renamed to `.corrupt-<timestamp>` before the next atomic write, the first render is never recorded and a query for an unknown artifact answers as revision 1. The exact authenticated route `GET /api/intelligent-ui/artifact-revisions?artifactId=&revisionId=` via `connection.requestRejection` is unchanged (JSON, `no-store`, 400 `invalid_input` for invalid params, 405 for other methods), and the same route now accepts an authenticated `DELETE` to remove a record; the client checks the latest revision when entering edit mode, before sending and on retry, and treats the check as unknown without `webServer`/`connection` (editing is not blocked).

## Update notice (npm latest)

- **Host**: `GET /api/intelligent-ui/update` (authenticated through the same `connection.requestRejection` as the other routes) reads the npm `latest` dist-tag (six-hour success cache, five-minute failure cache, five-second timeout). Only a *stable* version newer than the running one counts; an unreadable or prerelease running version answers `updateAvailable=false` instead of a false positive. When an update exists it then reads the tag-pinned `https://raw.githubusercontent.com/<repo>/v<latest>/release-notes/<latest>.md`, taking up to six `## Highlights` bullets (Markdown markers removed). The client sends the active DSH locale as `?lang=…`; ids starting with `en` prefer `<latest>.en.md` and fall back to the default (Chinese) file when the English file is missing or has no Highlights, with a separate cache per variant. A failed notes read still returns the version with empty highlights and retries on the failure TTL.
- **Client**: `src/client/sidebar-update.ts` inserts one normal-flow host before the sidebar panel `<nav>` (DSH 0.2.2-rc.1 has no slot there; an unknown shape inserts nothing). `UpdateNotice.tsx` renders the card; clicking it opens a fixed popover (to the right when it fits, below the card otherwise) that lists the points. The "View details" label only opens the popover; clicking the rest of the card (including the always-right arrow) calls `pluginNavigation.openBundle` for this bundle's detail page; outside click/Escape closes it, and the card hides when the sidebar collapses to the rail.
- **Publish gate**: `release-notes/<version>.md` must be human-reviewed and committed with the version; `publish.yml` runs `npm run check:release-notes` before publishing and refuses a missing file or an empty `## Highlights` section. Once the tag exists the text the card reads cannot drift.

## Layout and spacing contract

For an Auto-chosen free layout, free temporary results or selected free templates, the page-shape and typography guidance below is advisory; follow the composition the content needs. Component flow spacing, language, theme and safety rules still apply.

- **The renderer owns the vertical rhythm**: the page root `Col`, `Section` bodies and `Card` contents are flow-spaced (page 24px, group 12px, inner 8px). The model should not pass `gap` there; an explicit gap overrides or doubles the rhythm.
- **Explicit gaps are for rows and compact groups**: `Row`, `Grid`, `Carousel` and small control stacks may use 1–2 (inner) or 3–4 (group); do not use a nested `Col` with 5–6 to imitate page spacing.
- **No manual blank space**: `Spacer()`, empty `Box`/`Col`/`Card`, empty `Text`/`Markdown`, and a `Divider` used as a blank create uncontrolled blank bands; group with a `Card`, otherwise let the flow space the blocks.
- **Fallback chain**: the generation prompt and the Agent Skill carry the same contract; the Host's `layoutWarnings` returns non-fatal warnings for root gaps, vertical Spacers, empty Sections/Text and `gap: 0` block stacks so the model can repair them in the same turn; the renderer itself guarantees Section bodies are nested flows and the Article root keeps a single page gap.

## Decision policy

The switch only makes the capability visible; the policy that decides whether a turn gets a page and which layout it uses lives in one place — the injected `tool:intelligent-ui` prompt section (the Host also prefixes it with "Intelligent UI is enabled for this session" and appends the effective style note). An enabled session behaves as follows:

- **The model decides whether a page helps (Auto has no default):** it uses `render_ui` when showing the answer helps the reader understand faster or more accurately — a concept, mechanism/process, structure, comparison, data or interaction; a bare fact, a term restatement, a one-sentence definition that does not explain how something works, code/translation, chit-chat or an explicit text request stays in Markdown. When both seem to fit, the kind decides: an explanation of how something works is a page even when the prose version would be short.
- **The style only decides the layout when a page is rendered:** a `Card` page stays compact and scannable; the `Article` style calls for an article-first page — a `Toc`, collapsible `Section`s, and substantive `Markdown` prose for every major part (a skeleton, or content hidden behind interactions, is not acceptable); `Auto` lets the model choose Card, Article or a free layout.
- **Explicit render requests:** `/intelligent-ui` or an explicit page/dashboard ask, on-demand generation and artifact edit requests still require a page.
- **One source:** the Agent Skill does not repeat the decision policy; it only covers how to build.
- **Experimental document mode:** when on, an ordinary answer's prompt switches to the whole-answer document contract (no Markdown reply, `style: "free"`); it changes only the rendered presentation and the prompt, never the page-vs-text decision. On-demand generation, edit requests and explicit render requests are unaffected.
- **Free-form layout switch:** the plugin detail page writes a volatile field in the Host settings document. When on, the design playbook becomes advisory. It is orthogonal to the answer style and does not replace it; an Auto session may choose the free layout regardless of this switch.

## Image export

- **Entry:** the extension contributes an entry to DSH's `conversation.chat.assistant-actions` list (the standard copy / like / branch strip) and uses `order` plus `margin-left: auto` to sit at the **far right** of that row, styled as a labeled export pill to stand apart from the native icon controls. ### Edit pipeline: structure queue, explicit saves and total Apply preview (2026-11-10)

- **Root cause**: a batch or per-row structure operation used to submit immediately and call `markSubmitted`, closing the editor and losing the block requests and global instruction the user had typed. Every structure operation (batch toolbar plus the row-menu delete/duplicate/move) now enters a **pending round queue** first and never writes the Host on selection.
- **Batch mode**: entering snapshots `targetOrder`/`nestedOrder` panel-locally; batch duplicate/delete only append to the panel-local `batchOps` draft (shown as "N unsaved structure operations", removable one by one) and send no request. **Save batch** queues the already-applied order plus the batchOps and exits; **Cancel** or Escape restores the order snapshot, drops the batch draft and exits. Row-menu delete keeps its two-step confirmation before queueing, duplicate/move queue directly, and all of them announce through `aria-live`.
- **Pending-this-round section**: structure queue rows (with per-row remove), saved block-request/addition counts, the global instruction (panel-local draft plus an explicit **Save global instruction** action and a saved/unsaved state) and the order state. Only a saved global instruction reaches the draft, the composer chip and the "pending edits" dock summary; queued operations are counted in the chip, and a queue-only draft reports "N structure operations" instead of pretending to be a global note.
- **Bottom Apply**: the fixed `data-dsh-iui-edit-apply` button is disabled with nothing saved. It calls `previewPendingStructureOps` to fetch the authoritative `preview:true` dry run and opens the total preview dialog (`aria-modal`, initial focus on cancel, Tab trap, Escape close, focus restored to the trigger): structure operations, diff, involved blocks, model-request summary (block requests/global/order/additions/style) and the conflict list, with loading/failed (retryable)/ready states. With no queued operations only the model summary is shown. Conflicts disable the confirm button and each one explains how to resolve it.
- **Apply execution**: `applyEditRound` submits the queue as one atomic batch (`resolvePendingStructureOperations` serves both the preview and the real submit: delete/duplicate descend by base index within a parent, duplicate `toIndex = index + 1`, mixed kinds or more than one move in a parent are rejected as an `order` conflict, and a within-parent move uses the post-removal index with the redundant `toParentNodeId` omitted), records one local `kind:'structure'` revision, then `rebaseDraftAfterStructure` rekeys the draft onto it. A confirmed total preview reuses its dry-run program as the Apply preflight (a fresh dry run only when the queue identity changed), so one Apply sends one dry run plus one real batch. `remap.ts` first simulates the batch's post-order sibling slots (deletes remove a slot, duplicates sit directly after their source, moves append to the target parent), then aligns that simulation position by position with the authoritative Host result: copy slots never claim a mapping (an identical-text copy cannot steal the next sibling's saved request), container blocks (Col/Row/Box/Grid/Card/Carousel) are paired by type + position because their display title is derived from their first child, and `nestedOrder` inserts batch-created children at their base anchor so a pure duplicate is not reported as an arrangement change. Selection/additions/targetOrder/nestedOrder are remapped, the global/style instruction, branch, strict and nested mode stay, and the new chip is upserted before the old session/reference/persisted draft and chip are removed, so the composer never shows a dangling chip. Any unmapped request/addition/nested child or unreliable mapping (for example duplicate+move) blocks Apply in both the preview and the Apply preflight instead of dropping user work. A pure structure Apply closes the editor after recording the revision.
- **Automatic model send**: when model content remains after the rebase the card calls `requestArtifactAutoSubmit`: `composerHasPlainText` guards, and `inputActions.submit()` runs only when the composer is plain and the new chip is in place (≤12 × 400 ms probes). A failure or user prose in the composer keeps the chip and shows an `applyNotice` ("the model request is in the composer — send it manually") on the rekeyed panel.
- **Conflict rules** (block Apply during preview; no Host request is sent): a queued delete whose block or container descendant is still referenced by a saved block request/addition (`selection`/`addition`); a style instruction mixed with structure operations (`styleMixed`); mixed operation kinds or multiple moves under one parent (`order`); duplicate queue entries (`duplicate`); a container together with one of its children (`overlap`); more than 20 operations (`limit`); a vanished block (`unresolved`); an unreliable post-batch mapping or an unmappable request/addition (`target`); a page beyond the supported CST depth (`depth`, while a nested move on such a page uses `nestedTarget`: "This page is nested too deeply to move a block into a nested container") or beyond the 200-node budget (`nodeLimit`, whose copy names the node budget instead of pretending it is a depth problem).
- **Order and quick props**: `targetOrder`/`nestedOrderChanged` still belong to the model request (no zero-model revision); `Divider`/`Spacer` quick props still use the deterministic structure route but now rebase on success, keeping saved requests, the global instruction, ordering and the pending queue instead of dropping the draft.
- **Deep pages**: `MAX_CST_DEPTH` moved from 4 to **10** (the root `Col` is depth 0; the real dashboard page is depth 5–6 with 83 CST nodes) and the client nested map plus the Host structure route share that constant, so root-level delete/duplicate/move on big pages now preview and apply. The nested editing UI still offers children up to display depth 4. When `nestedBlocksForProgram` cannot map the page, `resolvePendingStructureOperations` falls back to a Host-shaped root-level block table (same node ids/digests), so root operations still resolve. A page beyond the supported depth reports a `depth` conflict (a nested move on it reports `nestedTarget`); a shallow page over the 200-node budget reports its own `nodeLimit` conflict instead of pretending it is too deep. Neither case shows the misleading "no longer in this revision".

after `submit()` the existing `reconcileArtifactSubmissions` confirms the draft when the Turn closes (Host conflicts still use the existing banner); a normal Send is refused with `pending_apply` while the structure queue is unapplied (no `markSubmitted`, no draft loss); the preview and the real Apply share one side-effect-free model-request check, so style/block mixes, empty instructions, temporary-style order-only, recorded-but-unremappable revisions and invalid requests appear as zero-op preview conflicts and disable confirm, and cancelling a loading preview drops its late answer; post-Apply notices share the composer card's top band with the draft row: the `:has()` rule returns `[data-composer-overlay]` to flow, and the band's -8px top margin reaches the card padding through DSH's `display: contents` slot outlet (a direct-child selector would not match there), so a notice-only strip (Apply consumed its draft) still contributes height instead of painting over the input area; ### Per-artifact revision history (user feedback)

- Two entry points: the always-visible card-header history icon (the rendered revision number follows the icon when it is above 1, replacing the old standalone `Revision N` badge button) and the edit-panel header button. Both open the **current artifact's** history only, never a cross-artifact timeline.
- Host: `ArtifactRevisionStore.listForArtifact()`; `GET /api/intelligent-ui/artifact-history?artifactId=` returns newest-first metadata (`current`/`source`/`hasProgram`/`restorable`, merging the program-only initial revision); `GET /api/intelligent-ui/artifact-history/program?...` loads a program on demand; the existing restore route now accepts the initial revision (when the source record is missing but its program survives, style/styleId/temporaryStyle/title fall back to the latest record and the new revision is latest+1).
- Client: `ArtifactHistory.tsx` metadata dialog (Revision N, current, source, time, style, changed-block chips; no full-page preview). `hasProgram=false` shows unavailable; old revisions can be restored, reusing the zero-model local-revision pipeline and refreshing the list. Before a delete, `rollbackTargetFor()` picks the newest smaller revision with `hasProgram`, the program route loads it, and `artifact-edit/revision-fallbacks.ts` persists it per session in `localStorage` (up to 20). After the delete, `IntelligentUICards` redirects any tool-result card still rendering the deleted revision through `applyRevisionFallback()` (keeping `callId`/`requestId`, replacing program, revision number and style), and the redirect survives a reload; the export entry (`export-data.ts`) applies the same fallback. Normal cards address Host result snapshots with `resultIdOf(program)` (`revisionId ?? callId`); a redirected card is read-only and a fallback to the initial revision borrows `temporaryStyle` without a matching result snapshot, so Save as template and the footer Adjust are hidden there.  `localRevisionIds` suppresses fallback records for revisions owned by client-local cards; a redirected card carries `fallbackFrom` and is read-only so it cannot share an `editKey` with the revision's native card, and `resolveRevisionFallback()` follows chained deletions (retargeting older entries when a new fallback is recorded).
- Deletion: the same `GET /api/intelligent-ui/artifact-revisions` path accepts `DELETE` (same auth/`effect`/disposer). `ArtifactRevisionStore.remove()` refuses the initial render (404 `revision_missing`) and a revision still referenced as another record's `baseRevisionId` (409 `revision_referenced`); on success it atomically rewrites the registry and clears the retained program. Deleting the latest record is allowed (the next newest becomes latest). Before the DELETE the client picks and persists the rollback target; on success it redirects every card still rendering the deleted revision to that fallback, so those cards do not stay bound to a deleted record; **a card's own rendered revision offers no delete when no fallback target exists**. A `revision_missing` answer (for example after a lost response) is treated as converged: the matching local card is removed and history refreshes. The confirmation focuses Cancel, cancelling returns focus to Delete, and the warning is announced as status; already-rendered model cards stay and re-render at the fallback revision (the redirected card is read-only; if that target is deleted later the client follows the fallback chain with a depth/cycle bound of 20). A revision edited by any card's unsent draft cannot be deleted (the canvas would unmount and the chip would point at a removed base); a revision still used as a newer revision's base hides its delete with an explanation (the history response carries `referenced`); revisions owned by client-local cards are removed with the card, record no fallback and are never chosen as fallback targets; without an available fallback, deleting from another card still succeeds and cards still rendering the revision may stay stale.
- Limits: initial-revision inference depends on the program registry (an LRU-evicted initial program omits that row); the initial row borrows style from the earliest record; history listing does not touch the program LRU, bodies are fetched on demand.

### Local image sources (2026-11-09)

- **Shared policy**: `src/shared/image-source.ts` classifies an `Image` source — `http(s)` renders directly; `data:image/{png,jpeg,webp,gif};base64` is validated and rendered inline (≤512 KiB decoded); everything else is a path, rejecting NUL/control characters, `..` segments, `~` and any URL scheme (both workspace-relative and absolute paths are accepted), with a 10 MiB file cap, a 40 MP pixel cap pre-read from PNG/JPEG/GIF/WebP headers for local files and inline data URIs (unknown headers fall back to the on-load check), MIME sniffed from magic bytes, SVG recognized by content and mapped to its own `svg-unsupported` placeholder, protocol-relative `//host/x` normalized to https and `DATA:` accepted case-insensitively. The path grammar is input hygiene only; the boundary is the Host process's workspace-files read authority (which can read absolute paths outside the workspace), not a workspace sandbox.
- **Client read** (`src/client/image-source.ts`): reads bytes through `remote.workspaceFiles.stat/readBytes` (the DSH 0.2.2 workspace-files client namespace, the same Session read authority as the file preview), sniffs the MIME, and creates a same-origin blob URL with `URL.createObjectURL`; failures map to the renderer's placeholder problems. `src/client/index.tsx` binds it through an optional `ctx.inject(['remote.workspaceFiles'])`, so a missing service degrades local images to the unsupported placeholder while the plugin still loads.
- **Renderer** (`src/lib/components/image-source.tsx`): `ImageSourceProvider`/`useImageSource` own the loading/ready/error state and the blob URL lifetime (revoked on unmount); an explicit `Image` source that fails shows an error placeholder and never searches by `alt`; `SearchImage` is unchanged; Markdown `![alt](src)` uses the same resolver (angle brackets around a destination with spaces/parentheses); `OpenUIRenderer` gains an optional `resolveImage` shared by cards and the edit canvas, `Image`/`SearchImage` carry an explicit mode, so a non-string/dynamic `src` is an invalid explicit source and never searches, and inline data images get the header pixel check before becoming ready; an explicit source that is still resolving marks its container with `data-iui-image-pending` so export settling waits for it (Markdown images included).
- **Export**: PNG capture reads the live DOM, and a same-origin blob URL does not taint the canvas; the error placeholder counts as settled so export does not wait out its full deadline; offline mode only skips the search wait, while local image resolution still settles. The single-file HTML export waits only for local source resolution (`settleLocalImages`, short bound), not for image searches or remote loads, and collects only successfully resolved local images in the exported card set, grouped by card callId + source before inlining (portaled Popover content, failed/oversized/SVG local images and non-exported local revision cards render a placeholder). The single-file HTML export reads blobs back from live `img[data-iui-image-src]` elements as data URLs, passes them through the `mountIUI` `assets` map, and the standalone page builds its resolver from that map.
- **Compatibility and boundaries**: needs the DSH 0.2.2 workspace-files service; absolute paths resolve through the viewing session's authority and may point at a different file across sessions/devices; images are render-time snapshots with no live refresh; local images inside a sandboxed `HtmlView` are not supported, and SVG is rejected for path/data sources (an http(s) SVG URL still renders through the browser `<img>` behavior).

### Active revision stage and visibility fallback (M1, 2026-11-10)

- **Version store**: `src/client/artifact-edit/artifact-version.ts` is an in-memory `useSyncExternalStore` store keyed by `(sessionId, artifactId)`.
