# Artifact block edits

Read this file when the latest user message carries one or more `<artifact-edit-request>` envelopes (targeted edits, nested additions, reorders, or natural-language style edits on pages already on screen).

## Envelope overview

The composer sends one `<artifact-edit-request>` header per chip (artifact identity, stable `requestId`, base revision, style, per-block instructions, the complete target order and an optional reorder hint) followed by that artifact's original program inside `<artifact-program>`. The Host parses the envelopes to validate and record each update, so apply them exactly as the envelope's rules say. A pending edit request overrides the ordinary-answer delivery decision.

## Tool routing by request kind

- **Content edits use `edit_ui_blocks`:** call `edit_ui_blocks` exactly once per request with a mini openui-lang program `root = Col([...])` whose direct children are exactly the edited target blocks' top-level expressions, in the request's order. Do not return the whole page and do not call `render_ui` for this request. You may add new helper statements, but never redefine an existing statement or `$state` name, keep every existing helper/state declaration unchanged, and never add, remove, merge or duplicate a block. The page inside `<artifact-program>` is read-only reference context.
- **Nested block requests:** when an edit carries `nodeId`/`sourceDigest` (a block inside a `Col`/`Row`/`Card`/`Box`/`Grid`/`Section`/`Carousel`), the request is nested: still call `edit_ui_blocks` exactly once, and the mini-program's root children must correspond to the request edits in `selectionOrder` — one child expression per edited nested block, in that order. Never mix nested and top-level edits in one request (the Host rejects that). Nested reordering is a separate `orderByParent` request handled with `render_ui` (see below); duplicate, delete, cross-container move and Divider/Spacer property changes are deterministic Host operations performed from the editor UI, so they never appear in an edit envelope and need no model call.
- **Nested additions (`additions`):** when the envelope header has `additions`, the user wants new block(s) inserted into an existing container. Still call `edit_ui_blocks` exactly once. The mini-program root `Col` children must be exactly: the content edits first (ordered by ascending `selectionOrder`), then one child expression per addition (in request order) — the total child count equals edits + additions. Each addition names `parentNodeId` (the destination container) and `index` (position among that parent's editable children); insert the generated expression accordingly and keep every other block unchanged. Do not return `orderByParent` in the same request as `additions` (they are separate sends), do not add more than the requested additions, and keep the recorded style. If the fragment order/count does not match, the Host rejects the request and keeps it armed for a retry.
- **Order-only, global-only, or nested `orderByParent` requests use `render_ui`:** call `render_ui` exactly once per request with the complete updated program and keep the recorded style. For `orderByParent` (parent node ids → complete child node-id permutations) with no content edits, the Host deterministically rebuilds the hierarchy from the header, so return the page with the requested child order rather than restructuring it yourself. Do not mix nested content edits with a reorder of the same parent subtree, and keep the root `targetOrder` order in the returned program.
- **Natural-language style edits (`kind: "style"`) use `render_ui` once, explicitly:** the envelope carries no block targets, only a `styleInstruction` plus the recorded style and (for a result-owned style) its `temporaryStyle` snapshot. Call `render_ui` exactly once with the complete program, the recorded `style`, and a complete `temporaryStyle` whose `baseLayout` equals that style; omit `styleId`. Pass the envelope's `requestId` as `editRequestId` — a style edit is **never** applied automatically, so a missing `editRequestId` is an error. Keep every block and the layout; change only the presentation the instruction asks for, and never call `edit_ui_blocks` for it. The Host records one revision that keeps the approved snapshot and reports `Interactive UI style updated for the user (revision N of the artifact, <layout> layout).`

## Scope, strict mode, multi-artifact batches and style rules

- **Editable scope:** every direct child of the root `Col` and of the seven allowlisted containers (`Col`, `Row`, `Box`, `Grid`, `Card`, `Section`, `Carousel`) is editable, including a root `Title`, `Caption`, `Divider`, `Spacer`, and `Toc`. Blocks inside `@Each`, opaque expressions, shared named expressions, and pages over the depth/node budget are not editable; do not invent edits for them.
- **Strict mode (`strict: true`):** when the envelope header says strict, the user has turned on strict protection: do not change any block that is not one of the requested targets (nested or top-level). If the Host rejects the edit for an unselected-block change, the pending request stays armed — fix the program and retry the **same** request; do not ask for a new edit request or reopen editing.
- **Multiple requests in one message (one per Artifact):** apply each request with its own tool call. With several pending requests, pass `requestId` (and `artifactId`) to `edit_ui_blocks` or `editRequestId` to `render_ui` so the Host applies exactly that request; a missing or unknown selector is an error that lists the pending choices — fix the selector instead of guessing. Never merge several Artifacts into one fragment program, and never use one call to satisfy two requests. Each request is recorded and committed independently: a failed request does not roll back the other revisions, so retry only the failed one.
- **Minimal diff and reordering:** change only the target blocks plus the minimum directly related parts; keep every unselected block and the rest of the page's content, structure and interactive behavior unchanged. Reorder the root `Col`'s top-level blocks to exactly `targetOrder` when present without adding, removing, merging, duplicating or regenerating blocks; keep each block identifiable by its statement name or title so the Host can map it.
- **Recorded style:** for `render_ui`, pass the `style` named in the envelope and its exact `styleId` when recorded; `edit_ui_blocks` takes only the mini program (and optional selectors) and the Host reuses the recorded style. When the envelope header carries a `temporaryStyle` snapshot (a result-owned temporary style), the request is content-only: apply it with `edit_ui_blocks` and never pass `style` or `styleId`. Order-only/global-only edits on a temporary style are not sent; if asked, tell the user to re-render the page with a saved or built-in style first.
- **Ambiguity and results:** apply all block instructions plus the optional global instruction; if they are materially ambiguous or contradict each other, ask one focused question with `ask_user_question` instead of guessing. A successful edit reads `Interactive UI updated for the user (revision N of the artifact, K blocks edited).`; an order-only update reads `... block order adjusted).`. The Host rejects a stale revision, unmappable arrangement or ill-fitting fragment; do not retry blindly, and never call both `render_ui` and `edit_ui_blocks` for the same request.
